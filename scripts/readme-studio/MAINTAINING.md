# README 维护流程

> 角色：规范　类型：流程　状态：现行（2026-11-17 建立，Task 0022）
> 适用：任何人或 Agent 要改仓库根的 `README.md` / `README.zh-CN.md` / `docs/images/` 时，按本文走。
>
> 本文只写**怎么维护**（流程、门禁、症状→原因）。素材怎么"演"在 `DIRECTOR.md`，工具怎么跑在 `AGENTS.md`。

## 0 为什么需要这份流程

README 是唯一一份**每个访问者都会看**的产物，也是最容易腐坏的一份：

- 它不在任何测试的默认视野里（`pnpm test` 跑的是代码）；
- 它的两份版本（中/英）靠人同步，一定漂移；
- 它的图不是代码，改代码不会让图变旧——**只有人眼能发现图过期**。

本仓库已经在这三条上各栽过一次（见 §5）。所以流程的每一步都对应一次真实的失败。

## 1 四类改动，四种走法

先判断你这次改的是哪一类，不同类的验收不同：

| 类型 | 例 | 必须做的验证 |
|---|---|---|
| **A 文字内容** | 改特性描述、改措辞、加一节 | `pnpm test`（doc-links 门禁）+ 人读一遍 |
| **B 新增/替换图片** | 换某张截图、加一个新特性动图 | §2 的完整拍摄流程 + `pnpm test` + **看图**（不是看文件名） |
| **C 结构变化** | 加/删章节、调顺序、改目录结构 | 两份 README 的 `##` 序列必须同步 + `pnpm test` |
| **D 与代码同步** | 代码改了导致 README 的某句话/某张图不再成立 | 先改代码提交，**再**回来改 README；不许一次提交里混着做 |

## 2 改图片的完整流程（最容易出错的一类）

### 2.0 一条命令跑完（日常用这个）

```bash
# 三件套先起好（§2 第 2 步），然后：
STUDIO_APP=http://127.0.0.1:<前端端口> node scripts/readme-studio/refresh.mjs
```

它做四件事：体检三件套 → 按固定顺序跑 8 个 storyboard（7 GIF + 1 静态图组）→ 打印每张图的体积与"是否变化"→ 跑 doc-links 门禁。
只重拍某几张：`--only=hero,theme-tour`；跳过门禁：`--no-check`。

**为什么要有这个入口**：README 会频繁更新（用户 2026-11-18 要求）。记住 8 个 storyboard 名字容易漏，漏一张就是"图与界面不同步"——那正是 C218 的返工来源。

> `stills` 放在最后跑：它要在"界面已就位"的状态下拍；前面的 GIF 跑完，页面状态更稳定。

### 2.1 手工单跑（调试某一项时）

```
1 确认前端代码是不是最新的
   └─ 素材必须基于当前 main 的代码拍。判断依据：git log 里的视觉改动 vs 图片 mtime（§5 案例 C-0022-01）

2 起拍摄环境（三件，缺一不可）
   ├─ 演示实例：LIFEOS_HOME=~/.lifeos-showcase node --experimental-strip-types src/main.ts --port=<分配>
   ├─ 前端：VITE_DEV_API=<后端> pnpm --dir frontend exec vite --port <分配>
   └─ 打桩模型：node scripts/readme-studio/stub-model.mjs
      └─ 为什么必须：真实网关会 402 余额不足，画面里是红色错误条（§5 C-0022-02）

3 写/改 storyboard（先填镜头表，见 DIRECTOR.md）
   └─ 每个镜头：演什么 / 时长 / 画面要求 / 角标

4 拍
   node scripts/readme-studio/run.mjs <name>

5 自检（七条，缺一不可）
   ├─ 抽帧看：这一帧是不是"想表达的那件事"
   ├─ 看开头：没有白屏（findContentStart 已自动跳过，但要确认跳对了）
   ├─ 看细节：正文最小区块缩到 390px 宽还认得出
   ├─ 无失败条 / 无凭据 / 无内部用语（demo-model、data-testid）
   ├─ 有角标（多例并列时）
   └─ 体积：单文件 ≤10MB（GitHub 上限）

6 接进 README（两份都要）
   └─ 位置：图放**组末或条目下方**，不集中成相册

7 跑门禁：pnpm test
```

## 3 门禁（机器能查的部分，不要靠记性）

| 门禁 | 查什么 | 在哪 |
|---|---|---|
| `test/doc-links.test.mjs` | ① 全部 README + `docs/` 的相对链接与图片路径可解析；② 两份 `##`/`###` 层级序列一致；③ 语言互链双向；④ **两版引用的图片集合完全相同**；⑤ 媒体数 ≥15 / GIF ≥6 / 章节 ≥18 / 代码围栏 ≥5（下限断言防"删空仍全绿"）；⑥ `LICENSE` 与 `FUNDING.yml` 存在 | `pnpm test` |

**下限断言的用法**：新增图片时不用改它们；只有当内容被大量删减（例如拆出 `docs/features.md`）时才同步调整，且要在提交信息里写明原因。

## 4 什么算"改完了"

- [ ] `pnpm test` 全绿（含 doc-links）
- [ ] 两份 README 的 `##` 序列一致、图片集合一致（门禁已覆盖，但人也要扫一眼措辞是否同步）
- [ ] 新增/替换的每张图**亲眼看过的**（不是"脚本跑成功了"）
- [ ] 图里没有：失败提示条、真实凭据、内部用语（`demo-model`、`data-testid`、`stub`）
- [ ] 若图里出现未实现的功能 → 必须在 Roadmap 而非 Features，且带「未实现」水印
- [ ] 提交信息写清「改了什么图、为什么重拍、基于哪个 commit」

## 5 反面案例（本仓库真实发生过的，每条都付过代价）

### C-0022-01 · 图是用旧界面拍的（2026-11-17）

**现象**：7 个 GIF 全部拍完后，用户看 README 说「老的感觉都没有新的好看」。对比发现 6 个 GIF 的 mtime 早于 main 分支合入的时间——它们拍的是合并前一天的界面。

**代价**：7 个 GIF 全部重拍（约 1 小时），且中间还踩了下面 3 个环境坑。

**正确做法**：
1. **拍之前先对时间**：`git log -1 --format=%cd` 与 `ls -l docs/images/*.gif` 比；main 上有改动 `ui.tsx` / `tokens.css` / `index.css` 的提交在两个 mtime 之间 → 必须重拍。
2. 拍完在提交信息里写"基于 commit `<sha>`"，下次就能直接判断是否过期。
3. 判据不是"我看界面好像没变"——Task 0017 的 wash/fill 分离、行圆角统一都是稳定的视觉变化，凭肉眼很容易漏。

### C-0022-02 · 素材里出现红色"模型调用失败"（2026-11-17）

**现象**：第一次拍的 `hero.gif`，第 8 秒左侧一个红色块写着「模型调用失败 · Connection error · 2s 后重试」。

**根因**：拍摄用的演示家目录里，模型配置还是真实网关；实拍时网关返回 402 余额不足。

**代价**：那张 GIF 作废；后续又踩两次（只改系统 `settings.json` 不生效——优先级是 Agent 个人 → 系统 → 清单）。

**正确做法**：
1. `run.mjs` 已在拍摄前 ping 打桩服务的 `/v1/models`，不在就整轮失败——**不要绕过这个检查**。
2. 打桩要覆盖到**真实生效的那一层**：把 `models.json` 里**所有 provider 的 `baseUrl`** 指向打桩，而不是只改 `settings.json` 的默认值。
3. 自检必须逐帧看，不能只看首尾两帧。

### C-0022-03 · `trimEnd` 取错方向，整段拼出来是白帧（2026-11-17）

**现象**：多镜头拼接后，某几段是纯白。

**根因**：`trimEnd` 被实现成"取开头 N 秒"，而展示型镜头前面恰好是页面加载 + prelude 重载 + 切会话——开头 N 秒全是白屏/骨架屏。

**正确做法**：展示型镜头取**末尾** N 秒。代码里已改为 `from = max(contentStart, full - N)`，注释写明原因。

### C-0022-04 · 两版 README 图片集合漂移（2026-11-17）

**现象**：改英文版时用 `git checkout README.md` 还原，把刚写进去的 18 处图片引用冲掉了；中文版还留着 → 两版图片集合不一致。

**代价**：门禁报红，需要按顺序重建英文版的 18 处引用。

**正确做法**：
1. 改文件前先 `cp` 到 `/tmp` 备份再改（**不要用 `git checkout` 还原未提交的成果**——它回到的是最后一次提交，不是你刚改之前）。
2. 门禁的「两版图片集合相同」这条断言就是为了抓这个；看到它红，先 `diff <(grep -o 'docs/images/...' README.md) <(... README.zh-CN.md)` 定位。

### C-0022-05 · 测试残留与真实凭据混进素材数据（2026-11-17）

**现象**：把真实家目录复制成拍摄用的 showcase 后，会话列表里全是 `草稿契约-1794873054555` 这类测试残留标题；另有 13 个会话文件含真实 API 密钥（`sk-amr-...`）。

**代价**：需要写脚本清理，且**凭据一旦进图/进 Git 就是安全事故**。

**正确做法**：
1. 复制真实数据做演示环境时，**必须先扫凭据**：`grep -lE "sk-[a-zA-Z0-9_-]{20,}" ...`，命中的会话直接删。
2. 测试残留会话（标题形如 `<名字>-<13 位时间戳>`）也要删——它们会出现在列表里。
3. 这两步应该写进复制脚本，不靠记得。

## 6 症状 → 先查什么（排障索引）

| 症状 | 先查 | 依据 |
|---|---|---|
| 图看着像旧版界面 | main 上有没有改视觉的提交落在图片 mtime 之后 | C-0022-01 |
| 图里有红色错误条 | 打桩服务在跑吗；`models.json` 的 provider baseUrl 指向哪 | C-0022-02 |
| GIF 某段全白 | 该镜头的 trim 取的是开头还是末尾 | C-0022-03 |
| GIF 体积失控 | 时长 × 约 300KB/秒；先降 fps 再降宽度，别降可读性 | `AGENTS.md` 的体积表 |
| 中文字幕/角标出方块 | 字体必须显式给 fontfile | `AGENTS.md` |
| 检视面板里看不到图 | 相对路径 + `/api/review/raw` 是否生效 | Task 0022 的实现说明 |
| 两版 README 不一致 | 门禁的章节序列/图片集合两条断言 | C-0022-04 |
