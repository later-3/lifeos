# 问题定位修复（troubleshooting）

> 角色：任务类型规则　类型：规范　状态：现行（2026-10-24 用户指示）
>
> 类型语义独立于 development（后者"从没有到有"，本类型"从不正常回到应该"）。三类问题：A 仅定位 / B 直接修 / C 转需求。
>
> 语气分级：本文件用协议 §3.3 的"必须 / 应该 / 可以"三级标注；违反"必须"构成缺陷，违反"应该"记原因于 log，"可以"视场景自选。

**Task 的"本任务遵守"区块**（由协议骨架自动生成）会同步带上：code specs 5 份、项目流程文档、参考基线、项目仓库约定。这些是"开发类与修复类"共用的规范。

## 1 流程步骤（三段：定位 / 修 / 沉淀）

### P1 定位（A/B/C 共用）
- **必须** 明确现象：用户可复现、含时间与环境；不在假设上写代码；
- **必须** 收集证据：`~/.lifeos/logs/*`、会话 JSONL、代码源文件、"turnId / sessionId / reqId" 等键；**应该** 先看再解读；
- **必须** 写出根因：因果链（现象 → 差异 → 差异来自哪个模块哪一行），**是"能查证的"而非"猜测"**；**应该** 一条一行列出；
- **必须** 行业参考：查 `reference-baseline.md` 的场景行 / 2-3 个代码库里看同类情形；若判定为独有，**应该** 在案例里写明"为什么是独有"；**禁止** 凭经验闭环；
- **必须** 判断类别：若判为架构层问题，应转 C 类别、以 development 类型新 Task 承接修复方案（类别判据在类型模板）；**应该** 搜同类代码点（用户第 4·b 条）。

### P2 修（只有 B/C 场景）
- **必须** 先写红测（T? 编号），再写代码（`specs/code/testing` 的条文同时适用于本流程）；
- **必须** 修完跑 `pnpm test` / `pnpm test:ui` 不退化（依赖改动大时优先 `pnpm test`）；
- **应该** 记录回滚方案（一旦测试挂了怎么撤）；
- **可以** 临时小工具在 Task 目录里自建（必须 log 记录，不用另拍板）。

### P3 沉淀与收束
- **应该** 有可复用结论时回填 flywheel；**应该** 有"违反"时回填 cases（正 / 反）；
- **必须** 按 `development/AGENTS.md` 收尾清单五条收束（状态 / 知识回流 / 规范·飞轮 / 案例 / 待办）；
- **可以** 提升到高层 or 协议层（视"谁必须遵守"判据）。

## 1.5 过程记录与证据（必须 · 定位可复核的底线）

**必须** 在 `log.md` 记录**定位过程**，而不是只写结论。每条一行、带时间，格式：

```
HH:MM 假设：<我认为问题可能出在 X>
HH:MM 验证：<读了哪个日志/跑了什么命令/看了哪段代码>
HH:MM 结果：<看到什么原文，支撑还是推翻假设>
HH:MM 结论：<当前判断 + 还剩什么不确定>
```

**必须** 在 `evidence/` 保存**过程证据**（见该目录 AGENTS.md）：日志摘录、命令与原始输出、截图、链接、配置快照；一条证据写清**来源 / 时间 / 原文 / 能证明什么**。

**必须** 在 `01-background.md` 的「证据收集」里**点名引用**证据文件，不写"我查过了"这种无证据结论。

**应该** 一条证据只回答一个判断；找不到证据时明确写"未找到"，不编。

**可以** 证据类型不限（md/txt/png/json/链接）。

## 1.6 修复方案的内容要求（必须）

`02-fix.md` 里的方案不允许只写"我改了 X"。**必须** 包含：

1. **候选方案 ≥ 2**：做法、优点、代价/风险、结论；
2. **选型理由**：为什么选当前这个，而不是其它（最小正确面？还是要一次性解决架构问题？）；
3. **行业/上游核对**（对应"不闭门造车"）：
   - 这个问题是**我们独有**，还是行业普遍？（给出依据）
   - 行业/上游**是否已有成熟解法**？（Pi SDK / pi-web / LibreChat / Open WebUI 等）
   - **我们是不是 API 用错了**？（上游明明有能力，我们没接）
4. **证据引用**：核对过程的材料放 `evidence/`，正文点名引用。

**禁止**：不看上游、不给候选、不说理由，直接写"已修复"。

## 2 三条硬约束（对违反即缺陷）

1. **基于事实分析**：不懂/不明第 1 反应是问用户；**禁止** 懂装懂或假装跑通；
2. **依据客观标准**：功能预期 + 代码事实 + 行业参考；**用户的话 / Agent 的话都不是绝对标准**（作为一次"现象"，仍要进入 `case` 记录链）；
3. **完善文档记录**：task.md（唯一状态源）+ 01-background（现象 / 证据 / 根因 / 行业参考）+ `cases/<日期>.md`（按 protocol §3.4 的三段写法）。**禁止** 只在对话里说完就把问题"以口说"当作完成交付。

## 3 "判断转需求"的判据

类别 C 的适用判据（满足其一即转）：

- 单点修无法避免回归（改一个模块就 разруш另一个）；
- 根因在**架构层**或协议层；
- 涉及"其他模块 / 其他模块协议 / 数据模型改变"；

不满足上述判定 → 按 **B 直接修** 局部处理。类型分界由类型规则说明 + Agent 专业判断，**必须与用户（或用户委托的其他 Agent）对齐再转 C**。

## 4 "同类风险"判别步骤

1. 按"同"字搜索（`rg "同<关键字>" src/ --glob`）；
2. **应该** 至少查 2–3 个可能同类点；
3. **必须** 明确列出"已修的 / 未修但可能修的"列表（B 类贴在 02-fix.md 的"同类修"节）。

## 5 心智模型（反串讲核心）

 ремон 定位的**事实合法来源**有三：**功能预期**（所以先问"这场景本来应该怎么表现"——有些问题正是"预期没定义"）；**代码事实**（git diff / grep）；**行业参考**（不闭门造车）。**用户的话 / Agent 的话**可以作为线索，但**不能作为"确定"的原因**；有分歧必须回到上面三事实重新查。

## 6 与其他规范 / 骨架的联动
