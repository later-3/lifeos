# 开发类 Task（development）

> 角色：任务类型规则　类型：规则　状态：现行

## 承载什么

- 一件需要改动、交付或验证的工作：目标、背景、步骤、过程、结论；
- 类别决定必需文档：A 改产品行为（背景、设计、阶段、计划）；B 改协作规范（背景、计划）；C 只出结论（背景）。详见 `template.json`。

## 怎么维护

- `log.md`：记过程与重要事项，只追加，带时间；
- `task.md`：维护整体状态——做到哪一步、剩余哪些、是否完成、当前指针；
- 每一步需要的规范与要达成的目的，写在计划文档里；做完一步就更新状态；
- 发现的后续事项进 `todo/`；有可复用经验时更新 `flywheel.md`；值得记的事实写进 `cases/`；
- 状态由用户或 Agent 标记（如"已完成"）。这只是记录，不是锁：用户之后再问，可以把它改回"进行中"，继续写 `log.md` 与各文档。

## 开工先读（在"承载什么"里已隐含，此处点名）

1. **场景入口地图**：仓库根 `AGENTS.md`（开发 Life OS 时是本仓的项目指引）按场景列出前端/后端/接口/测试/检视的阅读顺序；
2. **代码规范正文**：`projects/lifeos/specs/code/<环节>/code.md`（或本 Task 遵守区块点名的路径）——写档前逐条浏览，写完按其条文自检；
3. **参考基线**：`projects/lifeos/knowledge/reference-baseline.md`——如果要参考一个项目，先看该场景一行是否存在；
4. **测试**：本 Task 范围里已把"测试怎么写"规范独立（`specs/code/testing/testing.md`），写测试先读它，并给自己的每一步先红后绿。
（正文编号与路径以 Task 的 `task.md` "本任务遵守"区块为准，本节只写"该怎么开始"。）

## 收尾清单## 收尾清单（每件开发任务的固定落盘动作）

任务收束（"已完成"之前）把这几件事做掉，缺一不算收束：

1. **状态收束**：`task.md` 状态与当前指针更新到最新事实（用户说"恢复了"就改回进行中，状态是记录不是锁）；
2. **知识回流**：实现位置变化时更新对应知识文档（`knowledge/architecture/…`），未实现且"以后要做"的登记 `todo/`（todo/todo.md）；
3. **规范/飞轮回流**：可复用结论 → 所在层 `flywheel.md`；新写成"该怎么做"的条文 → 对应层 `specs/`；只提炼，不搬正文，原处留指针；
4. **案例沉淀**：发生的事实（含用户报告的现场）→ 该 Task 的 `cases/<日期>.md`，编号连续；
5. ****完成/升级决策**：`todo/` 里已完成或已升级的条目删除或指向新任务；未完成且要继续的，一句话写清缺什么。

## 已拍板决策的记录惯例

- 用户拍板（选项、硬约束、位置）**集中记在 `01-background.md` 的"已拍板决策"节**；设计/计划/运行只引用，不再各自复述。
- 概念空间：本项目新词在 `concept-space.md` 落defs；先能用先写，跨任务仍会用才作为项目层词沉淀；先能用先写，收束复盘时再统一提升。

## 编码节奏（防"自作主张连续开工"）

- 停点/一口气必须**在本任务阶段计划头部与用户对齐并写入**，未经对齐不得连续开工多步；异常时随时停下对齐。

## 步骤与目标的对照（防止"偏着修"）

- 开发计划有两层承载：**计划层** `04-plan.md`（顺序与依赖、每步的规范与目的、验证方式），**步骤层** `phases/Pn-*.md`（一步一条：动作 → 遵循的规范条文 → 要达成的目的 → 测试方案 → 偏离对照）；
- **每完成一步**，回查该步"要达成的目的"与 01-background 的完成标准/已拍板决策：目标仍在就继续，偏离或发现新决定 → 把偏离写进 log，必要时先修目标（改背景/拍板）再继续；
- **收束时**，逐条判定完成标准与决策是否达成：达成/未达成/变更三种结论各带证据（测试或实测）；未达成的不标完成，转入 log 的"遗留"或新 Task。
