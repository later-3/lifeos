# 交互 harness 协议（v1 首版）

> 角色：架构 / 需求 / 开发　类型：说明　状态：**现行**（v1 定稿 2026-10-14；2026-10-22 增加对象、workspace、规范分层、默认 Task 与模板覆盖）

这是**协议本身**的正文。它不描述当前 `~/.lifeos` 里已有的组织（那里是实验状态，没有义务符合本标准）；
它规定"应该长什么样"，写完之后我们按它直接落地、直接测。

本协议的写法遵循它自己规定的逻辑：**先说什么是什么、由什么组成，再逐部分展开**（§1 → §2 → §3…）。

---

## 1 交互 harness 是什么

**交互 harness = 用户与 Agent 长期协作时，让"怎么协作"可以被积累、被遵守、被复用的一套协议。**

- 它约束的是**不同类型的任务该怎么完成**，以及**任务模板**；
- 它是**飞轮思想的载体**：每做一件事都让下一次更容易（§3.1）；
- 它是**独立于任何具体项目**的：项目有自己的规范与资料，那些属于项目，不属于本协议。

**边界**

| 包含 | 不包含 |
|---|---|
| 协作的规则、词汇、事实记录、可复用资料、任务与其类型 | 某个产品/项目的实现规范（那属于项目自己的知识库与规范） |
| 内容怎样被声明、被找到、被加载、被维护 | 具体某一次任务的内容 |

## 2 由什么组成

按**逻辑功能**分，而不是按目录名分（目录怎么摆是实现细节）：

| # | 组成部分 | 回答什么 | 形态 |
|---|---|---|---|
| 2.1 | **思想** | 为什么要持续这么做 | 一篇（当前是"飞轮"） |
| 2.2 | **概念空间** | 这套协议里的每个词指什么 | 一户一词，可自举（§4） |
| 2.3 | **规范** | 必须怎么做（可检查） | 按主题分文件 |
| 2.4 | **案例** | 当时发生了什么、代价是什么、正确做法 | **按日期**分文件（§5） |
| 2.5 | **日记** | 当时的过程与决定 | **按日期**分文件（§5） |
| 2.6 | **工具** | 有什么可复用的脚本／校验 | 按功能分 |
| 2.7 | **知识库** | 可复用的领域知识（带出处） | 按主题分 |
| 2.8 | **任务（两类：用户下达 / Agent 定时）与任务类型** | 这次做什么、这类任务怎么做 | 任务目录 + 类型细则（§6） |
| 2.9 | **层级与归属** | 内容属于谁、谁必须遵守 | 机制（§7） |
| 2.10 | **会话与默认会话** | Agent 与用户在哪里对话、第一条消息从哪来 | 会话目录 `sessions/` + 出厂预置的默认会话文件（§12） |
| 2.11 | **Todo** | 还没成为任务的一句话待办 | `todo/` 清单（§12.3；按需读，不进 prompt） |

这十一项是**功能**，不是“必须十一个目录”——实现可以合并（例如思想与概念空间同文件），但**功能不能缺**。
**不限定层数**：§7 只给机制，你要几层就几层。

## 3 逐部分展开

### 3.1 思想（飞轮）

**飞轮**：不把每次投入当孤立动作，而是让它成为下一次更容易的基础——行动 → 记录反馈 → 优化做法 → 下次更有效。

- 它是**协议内的重要思想**，不是独立板块：落地形态就是 §2.2–2.8 那些内容；
- **它自己在概念空间里有一个词条**（§4 自举），本文不再重复解释，只保留"为什么需要"这一层。

### 3.2 概念空间

- **一户一词**：一个概念一份正文；只解释"这个词指什么、不指什么"，不写规则、不记事实；
- **自举**：本协议自己的词（飞轮、案例、任务类型、层级、作用域…）**也在这里定义**；
- 索引只导航、不复制定义；
- 判定要建档：会被反复引用 / 曾出现实质误解 / 影响高影响决定 / 需独立修订。

### 3.3 规范

- 只写"必须怎么做"，可执行、可检查；
- 按主题分文件（一个主题一份正文）；规则变化时**改这份文件**，不新增平行的第二份；
- 规范条文应引用概念空间里的词，不自造词；
- **目录名用英文**：规范目录统一叫 `specs/`（一个主题一个子目录），不新建中文 `规范/` 目录；协议概念仍称“规范”；
- **存放与加载**：按 §16 的作用域放；加载时只读当前会话可见的层，逐层追加，**不做覆盖**；正文只有一份。

### 3.4 案例（按日期，§5）

- 只记**发生过的事实**：发生了什么 → 代价 → 正确做法；
- 分**正例 / 反例**两型；
- **实例按日期分文件**，一条一个编号，编号是引用锚点（`C159`）；
- 提炼：反复出现的模式 → 上升为**规范**或**原则**（放在规范里），案例本身不改写。

### 3.5 日记（按日期，§5）

- 记过程、决定、当时的上下文；允许流水账，但要可读；
- **时间戳必写**，由程序生成（不凭印象）；
- 日记里的内容可升格为案例/规范，日记本身不改写。

### 3.6 工具

- 只做**只读聚合/校验**，不写业务逻辑；按功能分（一个工具一件事）；
- 不按日期分：工具是"随时可用的能力"，不是流水记录。

### 3.7 知识库

- 存**可复用的领域知识**，每条带出处（文件/来源 + 日期）；
- 按**主题**分，不按日期分（查阅逻辑是按主题，不是按时间线）；
- 过期即废：来源变了要在条目里写明失效条件。

### 3.8 任务与任务类型

**任务（总类）** = 有目标、需要落盘、需要可追溯的工作单元。按「**谁决定开始**」分**两类**，二者同宗同源：

| 类型 | 谁发起 | 生命周期 | 落点 |
|---|---|---|---|
| **用户下达任务**（交互 harness 协议任务） | **用户**在对话里下达（"做个需求""定位这个问题"） | 一次性：做完即收束（可能跨多轮） | 一个任务一个目录 + `task.md`（**任务级**，§7） |
| **Agent 定时任务** | **系统**按**时间或事件**触发（无人值守） | 长期存在、**反复运行**；有状态（启用/暂停/取消）与每次运行历史 | 同样一个任务一个目录（`tasks/<NNNN>-<标题>/`）；每次运行有独立会话与记录 |

- **两类共用同一命名空间与字段**：`taskType`（领域，如 `development`）、`taskCategory`（类别：改产品/改协作/只出结论…）；
- **一次运行（run）** = 定时任务每次触发产生的一次执行；运行可以产出工作产物（写进该任务目录或既有约定的位置，如 `daily/`）；
- **任务类型之内可再分层，层数不限**（§7 的机制）：例如 领域 → 类别 → 步骤模板；
  判据是**能不能跨任务复用**：还能复用就再分一层，只能描述"这一次"就到底了（那是任务实例/一次运行）；
- 项目声明自己用哪些任务类型；不提前建类型，出现时再加。

## 4 自举：本协议用自己的概念空间解释自己

协议里的每个词都在 §3.2 的概念空间里有词条。**首版需要建档的词**：

| 词 | 一句话 | 不指什么 |
|---|---|---|
| 交互 harness | 用户与 Agent 协作的协议 | 不是某个项目的规范，不是产品实现 |
| 飞轮 | 让每次投入成为下次基础的思想 | 不是板块，不是文件 |
| 概念空间 | 词的唯一定义处 | 不是术语表，不是规范，不记事实 |
| 规范 | 必须怎么做 | 不解释词，不记事实 |
| 案例 | 发生过的事实（正/反） | 不是提炼出的规则 |
| 日记 | 当时的过程 | 不是案例，不是待办 |
| 任务 / 任务类型 | 工作单元 / 任务的领域 | 不是待办 |
| 层级 / 作用域 | 内容属于谁、谁必须遵守 | 不是目录深度 |
| 会话 / 默认会话 | 一次连续对话 / 随模板预置的第一条会话（第一句=Agent 打招呼与说明书） | 默认会话不是运行时生成的；第一句不是模型输出，也不是用户消息 |
| Todo | 一句话级待办清单 | 不是任务（任务有目录、类型与模板） |

## 5 大小与日期策略（回应"案例一直增加会不会太大"）

| 内容 | 按什么分 | 理由 | 索引 |
|---|---|---|---|
| **案例** | **按日期**（一天一文件） | 事实按时间发生，只会追加，不会改写 → 按日期切分最自然，单文件不会无限膨胀 | 需要（按编号+日期+一句话） |
| **日记** | **按日期** | 天然按天 | 不需要（按天查） |
| 规范 / 规范规则 | **按主题** | 会被改写与取代，不是流水 | 需要（主题清单） |
| 概念空间 | **按词**（一户一词） | 独立修订 | 需要（索引只导航） |
| 工具 | **按功能** | 随时可用，不随时间累积 | 需要（工具清单） |
| 知识库 | **按主题** | 查阅按主题 | 需要（主题索引） |
| 任务 | 一个任务一目录 | 工作单元 | 不需要 |

**共同要求**：凡"按主题/按词/按功能"的都要有**索引**（否则找不到）；凡"按日期"的都要有**编号**（否则引用不到）。
案例按日期分文件后，**跨日期的同类案例靠"编号 + 索引"串联**（不靠翻目录）。

## 6 加载与维护（机制）

| 规则 | 内容 |
|---|---|
| **按需加载** | 不是一上来把全部内容塞进 prompt：通用协议常驻；项目级/任务级/Agent 级在对应上下文里才加载 |
| **分级维护** | 谁的内容谁维护：任务级 → 改任务目录；项目级 → 改项目下的；通用级 → 改通用位置 |
| **提升** | 任意低层内容别处也用得上 → 可提升到任意更高层（任务 → Agent×项目 → 项目 → Agent workspace → 共享 workspace）；移动正文，原处**只留指针不复制** |
| **不复制** | 同一件事只有一处正文；跨层引用写链接与编号 |
| **历史不改写** | 案例与日记只追加；被取代的规范标注取代关系，不删除推理链 |
| **案例/日志不搬家** | 案例、daily、todo 留在发生层；只有提炼出的规范/飞轮正文可提升 |
| **模板是选择不是叠加** | 任务模板按 §16.4 四层覆盖选一份；规范加载才是逐层追加 |

## 7 层级与归属（机制，不限定层数）

**一条内容 = 名称 + 来源 + 作用域。** 作用域可嵌套任意层；加载时按 §16.2 从外到内**逐层追加**，**不做覆盖**（2026-10-22 用户裁决）。出现冲突时显式停下、由用户拍板或修改原文件，不能靠“后写赢”悄悄压掉。

| 维度 | 含义 | 典型层（示例，不是必须） |
|---|---|---|
| 作用域 | 谁必须遵守 | 所有 Agent → 项目 → Agent × 项目 → 会话 → 本轮 |
| 归属 | 谁拥有、谁维护 | 通用 / 项目 / Agent / 任务 |
| 声明 | 在哪被点名 | 项目声明自己用哪些任务类型；Agent 声明自己的偏好 |

**不写死层数**：需要第四层、第五层时就加一层，机制不变（顺序叠加 + 不覆盖 + 只引用不复制）。

## 8 待定（需与用户讨论后才定）

1. **既有架构文档能否用本协议转化**：初步判断——架构/模块文档属于**项目的知识库**（按主题、带出处），
   开发规范属于**项目规范**，案例与日记按日期；转化可行，但需要先补"主题索引"，且转化的只有组织方式，内容仍需逐份核对。
3. **规范与原则是否要分成两类**：本文只留"规范"（必须怎么做）；"原则"（凭什么判断）是否单列，取决于它是否跨任务类型复用。

## 9 项目、Agent 与 workspace（2026-10-22 校正）

**项目 = 用户的一个目录 + 一个全局身份。** 项目可以被多个 Agent 打开；同一个目录无论被多少个 Agent 打开，
都只有**一个全局 projectId**，但每个 Agent 有各自**私有的绑定层**（会话、记录、私有记忆）。

| 层 | 位置 | 放什么 |
|---|---|---|
| **用户工作区**（真实目录） | 用户自己的目录 | 用户的代码/文档；只作 cwd，不写我们的数据进去 |
| **全局项目层** | `~/.lifeos/projects/<projectId>/` | `project.json`（共享身份）+ `memory/`（共享记忆）+ `specs/`（项目共享规范） |
| **Agent 私有绑定层** | `~/.lifeos/agents/<agentId>/projects/<projectId>/` | `sessions/`、`daily/`、`cases/`、`todo/`、`tasks/`、`specs/`、`AGENTS.md`、`concept-space.md` |

- **顶层 `~/.lifeos/projects/` 必须保留**：它是全局共享层，不是旧数据；旧设计“取消共享层”的判断已废弃。
- **同 path 幂等**：打开同一个目录复用全局 projectId；把该 ID 绑定到当前 Agent 即可，不复制项目内容。
- **移除 = 取消该 Agent 的绑定**：写 `hiddenProjectIds`；全局项目、其他 Agent 的绑定、会话、记录全部保留。
- **目录即绑定**：Agent 私有目录存在即可用；外部项目的 cwd = 全局 `project.json` 的 `path`。

### 9.1 两个 workspace（同名，不同层）

| 名称 | 位置 | 作用域 |
|---|---|---|
| **共享 workspace** | `~/.lifeos/projects/workspace/` | 所有 Agent：共享 specs、共享记忆 |
| **Agent 私有 workspace** | `~/.lifeos/agents/<agentId>/projects/workspace/` | 单 Agent：默认项目、会话、daily、cases、todo、tasks |

共享 workspace 的 `project.json` 只有 `{schemaVersion,id:"workspace",name:"workspace"}`，**没有 `path`**；
它不是用户目录，而是所有 Agent 的公共资料层。私有 workspace 的 id 也叫 `workspace`，靠**所在层**区分，
不把共享层改名成 `shared`。

### 9.2 界面动作（协议要求）

| 用户动作 | 必须发生什么 |
|---|---|
| 打开目录 | 注册/复用全局项目 → 绑定到当前 Agent → 按需准备私有目录；不写用户目录 |
| 列出项目 | 只列当前 Agent 的绑定，减去它移除过的项目；默认项目置顶 |
| 从列表移除 | 只取消绑定；不删除全局项目、不删除其他 Agent 的绑定、不删会话与记录 |

## 10 协议怎样进入 Agent 的 prompt（加载约束）

协议正文、harness 本层指引、规范、任务类型与当前项目指引，必须由 **Life OS 的装配层显式读取**，
拼成 `<lifeos_interaction_harness>` 区域；Pi 的 `<tools>` / `<rules>` 仍由 Pi 自己的渲染结果回填。

- **常驻**：协议正文 + harness 本层指引 + 飞轮 + 概念索引 + 任务类型；
- **按作用域加载**：规范按 §16.2 的根顺序加载；任务级内容只在该会话选定 Task 时加载；
- **不跨项目**：当前项目之外的 `specs/` 不扫描、不注入；
- **可反查**：每个加载文件都记录来源路径，装配结果能回答“这句话从哪来”；
- **不做覆盖**：规范逐层追加；任务模板按 §16.4 选一份，不把四层模板合并。

## 11 常驻与"动作 → 落点"

### 11.1 常驻的那一小节写什么（"有哪些、在哪、何时读"）

```text
## 通用资产 · 能力与资料索引
- 协议：本协议（常驻）；任务类型细则见 task-types/<type>/（随协议常驻）
- 规范：共享 workspace → 当前项目共享 → Agent 私有 workspace → Agent × 项目（§16.2）
- 资料（按需 read）：案例 cases/<日期>.md · 概念 concept-space/ · 知识库 · 项目指引（项目仓库的 AGENTS.md）
- 项目：当前工作项目 = agents/<id>/projects/<pid>/（打开外部目录后就是该项目）
```

**只列"有什么、在哪、何时读"，不贴正文**——这是"按需读"能成立的前提。

### 11.2 动作 → 落点（现在有什么用什么）

| 动作 | 手段 |
|---|---|
| 读案例 / 概念 / 知识 / 项目规范正文 | Pi 的 `read`（按需，路径见常驻索引） |
| 创建 / 归档助手（多 Agent） | `lifeos_agent_create` / `lifeos_agent_delete`（Pi 工具，英文描述；归档 = 保留全部数据）；界面同语义为 `POST` / `DELETE /api/agents` |
| 创建 / 查看任务 | `lifeos_task_create`（编号 `NNNN-标题`、类别 A/B/C 决定必需文档）/ `lifeos_task_list`（按编号列状态） |
| 写日报 / 案例 / todo / 任务目录与 `task.md` | Pi 的 `write` / `edit`，落在 `agents/<id>/projects/<pid>/{daily,cases,todo,tasks}`；任务创建优先用 `lifeos_task_create` |
| 打开目录 / 从列表移除项目 | 界面（接口见 §9） |
| 找方法（Skill 描述进 prompt、正文按需） | Pi Skill |

### 11.3 通用层心智模型（用户 2026-10-14 确认）

> **只要规定好"从哪加载、加载什么、装到哪个区域、什么标签、什么顺序"，任何新内容都能自动填入对应 Agent 的区域。**

"声明表"（来源路径模式 → 区域标签 → 叠加顺序）**未实现**：现在由 `src/assembly.ts` 按固定顺序装配（见 §10）。登记在仓库 `docs/todo.md`。

## 12 会话、默认会话与项目私有骨架（2026-10-17 定稿；2026-10-22 补 specs/workspace/Task）

> 起因（用户 2026-10-17）：检查家目录模板时发现协议没写全——“project 下面的会话放哪、案例/概念空间/todo 归属、
> 谁说第一句话”在协议里是空白，骨架和协议对不上。本节补齐；“第一句话”最终定为**出厂预置文件**方案。

### 12.1 会话放哪

- **会话落在所属 project 的 `sessions/` 目录**：`agents/<id>/projects/<pid>/sessions/`；每个 Agent 的默认 project 是 `workspace`，默认路径 = `agents/<id>/projects/workspace/sessions/`。
- 这是**终态事实，不是计划**：出厂模板即按此结构携带会话，协议怎么写、磁盘就怎么放（结构即事实；协议只写事实，不写“待迁移”这类悬念——2026-10-17 用户裁决）。
- 会话文件格式沿用 Pi 的 JSONL（不自造）。

### 12.2 默认会话（第一条消息）

**它是什么（以用户表述为准）**：系统总要有一个与用户的**起手动作**——现在的产品靠网页说明书/文档说明书教用户，
我们的做法是**把说明书做成第一句话**：打开系统，Life OS Agent 先打招呼并告诉你可以怎么用，你顺着对话看就会用。
这一个起手动作有了就够：Agent 是大模型、协议在它的上下文里，它知道协议就知道后续怎么与用户交互，不再设计别的引导。

**形态与实现（零运行时动作）**：

- 默认会话 = **随模板出厂预置的 session JSONL 文件**（`agents/lifeosagent/projects/workspace/sessions/<ts>_<id>.jsonl`），
  第一条 message 条目即打招呼与说明书（assistant 角色）。
- **没有任何额外动作**：不读开场模板文件、不在运行时写入、没有触发条件——系统只是**加载**这个文件（Pi SDK 原生读会话文件，加载即显示）。
- 展示上它就是**一条普通会话**：无角标、无特殊样式，直接普通加载（2026-10-17 用户裁决）。
- **文件驱动**：预置文件只随 **Life OS Agent** 的模板装入；其他 Agent 没有默认会话，也不需要任何特判（2026-10-17 用户裁决）。
- 消息自带来源标识：`provider: "lifeos"` / `model: "opening"` 占位元数据——SDK 与反查能识别“这句是 Agent 发的、非模型输出”即可，不做额外动作。
- **两条口径**：① 会话记录口径：第一条 = Agent 打招呼（预制文本）；② 模型调用口径：**首次真实推理由用户对它的回复触发**。
- 上下文：用户回复后，这条消息本来就在会话历史里，模型自然承接。
- 文案宿主 = 预置文件本身（内容待用户后续打磨；改文案 = 改模板文件，不改代码）。
- **出厂显示名 `welcome to lifeos`**：预置会话文件内置一条 `session_info { name: "welcome to lifeos" }`（Pi 原生 name 机制，用户可随时改名覆盖）；界面不再出现“默认会话”字样。显示链（用户 2026-10-17 定）：`name ‖ 首条用户消息（后端全文、UI 截 50）`，**无兜底**。
- 用户删掉默认会话后，新建的会话是空白会话：说明书是一次性的，不复活（无触发条件的直接推论，2026-10-17 用户裁决）。

### 12.3 项目私有骨架（协议在 project 目录的落点）

每个 project 目录（含内置的 `workspace/`）就是协议在该项目作用域的实例，骨架：

| 骨架 | 对应协议板块 | 说明 |
|---|---|---|
| `project.json` | project 身份（**仅外部项目**） | `{schemaVersion, id, name, path}`；cwd = 它的 `path` |
| `AGENTS.md` | 项目指引（§7 作用域：Agent × 项目） | 本目录的规矩与指引；不复制协议正文 |
| `sessions/` | 会话（§12.1/§12.2） | 会话 JSONL；**出厂默认会话预置于此** |
| `tasks/<NNNN>-<标题>/` | 任务（§3.8） | 一个任务一个目录 + `task.md`（用 `lifeos_task_create` 建，编号按项目连续） |
| `daily/<日期>.md` | 日记（§3.5） | 按日期追加 |
| `cases/<日期>.md` | 案例（§3.4） | 按日期追加，编号引用 |
| `todo/` | Todo（§2.11） | 一句话级待办；不是任务，不进 prompt、按需读 |
| `concept-space.md` | 概念空间（§3.2） | 本项目层的词索引（正文按需读） |
| `specs/` | 规范（§3.3） | 本层规范；一个主题一个目录；`index.json` 是本层索引 |

- **按需建**：`tasks/` 预建（含 `AGENTS.md`），任务目录按需建；普通会话的当天默认 Task 由运行时取/建（§16.4）；每个预建子目录都有自己的 `AGENTS.md`；`daily/ cases/ todo/` 由模板带占位保证存在，`sessions/` 由出厂默认会话天然存在。
- **specs/**：本层规范；`index.json` 是索引（§16.3）。
- 项目是全局实体，可被多个 Agent 绑定；**会话、案例、todo、任务等私有记录只属于当前 Agent × 项目**（见 §9）。
- **workspace 双层**：共享 `projects/workspace/` 只放 specs/共享记忆；私有 `agents/<id>/projects/workspace/` 放会话与记录（§9.1）。
- **任务日期**：任务目录平铺为 `tasks/<NNNN>-<标题>/`，`task.md` 写 `日期：YYYY-MM-DD`；不按日期建物理目录，界面按日期分组（§16.4）。

### 12.4 加载方式（现状）

- **物理结构即终态**：会话读写直接使用 `agents/<id>/projects/workspace/sessions/`；不存在任何“迁移中”状态。
- 加载兼容：恢复会话按文件名 `<ts>_<id>.jsonl` 匹配 + `SessionManager.open(path, dir, cwd)`（带 cwdOverride），不走 `findById` 的 header cwd 过滤——出厂文件 header 的 `cwd` 为空，避免换机器/换目录 404。
- 历史：本节初版曾登记“待迁移”（实现滞后于协议时的悬念措辞），2026-10-17 用户裁决废弃——协议不写悬念，只写事实。

## 16 对象、作用域、规范与默认 Task（2026-10-22 定稿）

本节是 2026-10-22 讨论的落地规则；与前文冲突时以本节为准。

### 16.1 对象关系

```text
User 1 ── N Agent
Agent N ── M Project        （通过私有绑定 join；全局项目只有一份）
Project 1 ── N Task         （Task 属于某个 Agent × Project）
Agent 1 ── 1 私有 workspace （id=workspace）
Project workspace 1 ── 1    共享 workspace（全局特殊项目）
```

- **User**：最终决策者；取舍、风险、不可逆操作回到 User。
- **Agent**：执行者；有身份、模型、私有 workspace 与项目绑定。
- **Project**：全局实体；有共享身份、共享记忆、共享 specs；被多个 Agent 绑定时不复制内容。
- **Task**：有目标、可追溯的工作单元；属于 Agent × Project；是沉淀与迭代的粒度。
- **Workspace**：不是“第四个普通项目”，而是两层特殊作用域（§9.1）。

### 16.2 作用域与加载顺序

从外到内，逐层**追加**，不做覆盖：

```text
协议（常驻）
  → 共享 workspace specs（所有 Agent）
  → 当前项目共享 specs（projects/<projectId>/specs）
  → Agent 私有 workspace specs（agents/<id>/projects/workspace/specs）
  → Agent × 项目 specs（agents/<id>/projects/<projectId>/specs）
  → Task 级（tasks/<taskId>/specs 或 task.md 的“本任务遵守”）
```

规则：

1. **只加载当前会话可见的层**；不扫描其他项目、不把所有 Agent 的规范塞进来；
2. 同一份正文只加载一次；重复路径去重；
3. **冲突不自动覆盖**：停下、指出冲突层，由用户裁决或改原文件；
4. 任务模板是**选择一份**（§16.4），不是规范加载那样的逐层追加；
5. 加载记录来源路径；没有来源的内容不能当成规范。

### 16.3 规范（specs）

- 目录统一用英文 `specs/`，一个主题一个子目录；主题名用英文（如 `agent-collaboration`、`frontend-development`）；
- 每层有 `specs/index.json`（机器读）与 `specs/AGENTS.md`（人读说明）；索引只列本层正文；
- **规范 = 具体场景下必须怎么做，可执行、可检查**；不叫“原则”，不是 Skill，不是协议本身；
- 规范按场景生效：索引可声明 `appliesTo.scenes`；没有匹配场景就不加载；
- **原则**（凭什么判断）属于规范的一种内容，不另立一套平行目录；用户个人原则放共享 workspace specs；
- **提升可跨任意层**：低层 → 高层，或高层 → 低层；移动正文，原处留一行指针；不复制、不建平行第二份。

### 16.4 强制 Task、默认 Task 与模板覆盖

**每个 Agent × Project × 日期有一个默认 Task。**

- 当天第一场普通会话自动使用/创建该默认 Task；同一天同一 Agent × Project 的会话共享它；
- 会话通过 `activeTaskId` 引用 Task，**不是绑定**：同一 Task 可被多个会话引用，会话也可切换 Task；
- Task 是沉淀/迭代粒度：daily、cases、todo、任务规范、验收都挂到 Task 或从 Task 提升；
- **日期存储采用 B**：目录平铺 `tasks/<NNNN>-<标题>/`，`task.md` 的字段写 `日期：YYYY-MM-DD`；不建 `tasks/<YYYY-MM-DD>/`；界面按日期分组；
- 默认 Task 也遵守同一结构；它的标题可含日期（如 `daily-2026-10-22`），但日期事实以字段为准。

**任务模板四层覆盖（选一份，不合并）**，优先级从高到低：

1. `agents/<agentId>/projects/<projectId>/task-types/<type>/`（Agent × 项目）；
2. `projects/<projectId>/task-types/<type>/`（项目共享）；
3. `agents/<agentId>/projects/workspace/task-types/<type>/`（Agent workspace）；
4. `~/.lifeos/interaction-harness/task-types/<type>/`（协议默认）。

同一 type 找到第一份就用它；模板必须能给出：任务类型/类别、必需文档清单、`task.md` 骨架、验收口径。
模板变化要能追溯；不在运行时把四层模板拼在一起。

### 16.5 飞轮：思想、落地与文档

- **飞轮思想** = 行动 → 记录 → 提炼 → 下一次更好；不是“多写文档”。
- **落地** = 案例、知识库、概念空间、规范、飞轮文档共同承载；
- **飞轮文档** = 可复用的方法/洞察，不是过程日志；过程在 daily，事实在 cases；
- 飞轮文档可放任意层并提升；案例与 daily **不搬家**，只在原处留引用；
- 没有提炼出可复用结论时，不强行写飞轮文档。

### 16.6 案例、日志与“提升”的边界

| 内容 | 放哪 | 是否可提升 |
|---|---|---|
| 案例（正/反） | 发生的层 `cases/` | 不搬正文；可提炼成规范/飞轮并留指针 |
| daily | 发生的层 `daily/` | 不搬正文；可提炼 |
| todo | 发生的层 `todo/` | 升级为 Task 时移动条目 |
| 规范 | 对应层 `specs/` | 可跨层提升（移动正文 + 指针） |
| 飞轮文档 | 对应层 | 可跨层提升（移动正文 + 指针） |
| 概念词条 | 对应层概念空间 | 可提升；索引不复制定义 |

**判定提升到哪一层**：看“谁必须遵守”。只有当前 Task 用 → 留 Task；当前项目所有 Agent 用 → 项目共享；
当前 Agent 跨项目用 → Agent workspace；所有 Agent 用 → 共享 workspace；属于协作机制本身 → 协议。
