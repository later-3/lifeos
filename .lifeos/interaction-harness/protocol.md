# 交互 harness 协议

> 角色：架构 / 需求 / 开发　类型：说明　状态：**现行**（2026-10-23 按用户裁决全面更新：Task 为交互粒度、层级与结构同构、记忆并入协议、日记移出）

这是**协议本身**的正文。它规定"应该长什么样、怎么协作"。它不描述 `~/.lifeos` 里已有的实验状态，也不规定落地实现的细节（代码、工具本体、模板的具体内容）。

本协议的写法：**先说它是什么、由什么组成，再逐部分展开**。

---

## 1 交互 harness 是什么

**交互 harness = 用户与 Agent 长期协作时，让"怎么协作"可以被积累、被遵守、被复用的一套协议。**

- **交互以 Task 为粒度**：每次交互都落在某个 Task 里；Task 承载目标、过程、沉淀与状态（§3.7）。
- **结构同构**：Agent、项目、Task 各层的目录结构一致，内容不同（§5）。
- **它是飞轮思想的载体**：每做一件事都让下一次更容易（§3.1）。
- **它不是某个项目的规范**：项目自己的实现规范属于项目。

| 包含 | 不包含 |
|---|---|
| 协作的规则、词汇、层级与作用域、结构、沉淀的方式、Task 的定义与类型、会话与指针、记忆的层次与用法 | 某个产品的实现细节；某次任务的具体内容；标签词表、任务模板的具体步骤（这些随落地迭代） |

## 2 由什么组成

按**功能**分，不按目录名分。目录怎么摆是结构，结构在 §5。

| # | 组成部分 | 回答什么 |
|---|---|---|
| 2.1 | 思想（飞轮） | 为什么要持续这么做 |
| 2.2 | 概念空间 | 这套协议里的每个词指什么 |
| 2.3 | 规范 | 在具体场景下，怎么做才是对的 |
| 2.4 | 案例 | 发生过什么，正例还是反例，代价与做法 |
| 2.5 | 工具 | 有什么可以复用的操作，怎么用 |
| 2.6 | 知识库 | 项目或 Agent 需要的知识（带出处） |
| 2.7 | 任务与任务类型 | 这次做什么、属于哪种任务、怎么组织 |
| 2.8 | 日志 | 做了什么、哪些事情需要记下来 |
| 2.9 | 待办（todo） | 还没成为任务的一句话待办 |
| 2.10 | 会话与轮次 | 与用户的对话在哪里、一问一答怎么记录 |
| 2.11 | 记忆 | Agent 的能力：记住什么、记在哪一层、怎么用 |
| 2.12 | 层级与作用域 | 内容属于谁、谁必须遵守、按什么顺序加载 |

这十二项是**功能**，不是"必须十二个目录"。实现可以合并，但功能不能缺。

## 3 各部分的定义

### 3.1 思想（飞轮）

**飞轮**：行动 → 记录 → 提炼 → 下一次更好。不把每次投入当孤立动作，而是让它成为下一次更容易的基础。

- **飞轮文档**是承载这一思想的经验文档：可复用的方法、洞察，以及为什么。它不是过程日志（过程在日志里，事实在案例里）。
- **每一层都有一份飞轮文档**（`flywheel.md`），结构相同（§5）。
- **更新判据**：
  - 只对当前 Task 有效 → 更新该 Task 的飞轮；
  - 同一项目下多个 Task 都适用 → 更新该项目的飞轮；
  - 同一 Agent 跨项目适用 → 更新该 Agent 默认 workspace 的飞轮（Agent 本身不设飞轮，§4.1）；
  - 所有 Agent 适用 → 更新共享 workspace 的飞轮。
- **更新时机**：Task 有可复用结论时（不一定等它结束）。没有可复用结论时不强行写。

### 3.2 概念空间

- **只解释概念**：这个词是什么、在具体场景下是什么、它不是什么。
- **不记日志、不写规则、不记事实**。规则属于规范，事实属于案例与日志。
- **一个概念只定义一次**，定义放在它所属的那一层；其他层只引用，不复制。
- **每一层一份概念空间文档**（`concept-space.md`），结构相同。

### 3.3 规范

- **规范 = 在具体场景下，怎么做才是对的。**
- **必须先讲清本质**：为什么这样做才对，在什么场景下适用，做到什么程度算完成。不是堆条文。
- **表达方式可以是"应该怎么做"，也可以是"不应该怎么做"**。两种表达都允许，关键是场景和本质讲清楚，不缺"不应该"这一维。
- **按主题分目录**：`specs/<主题>/`，主题名用英文。规则变化时改原文件，不新增平行版本。
- **规范引用概念空间里的词**，不自造词。
- **规范是逐层追加、不覆盖的**（§4.3）。
- **语气分级（条文可检查性的一部分，写进任何规范/类型规则/任务条文时都要标）**：
  - **必须**：不按此做即缺陷，无例外；Agent 侧停手报告；
  - **应该**：默认场景做；偏离时在 log 记原因；
  - **可以**：由 Agent 视场景自选；
  每条条文以**必须 / 应该 / 可以**三词打头，禁止"尽量 / 务必 / 建议 / 要注意"等替代词；条文内部的分发要求由明确字说明，不允许模糊语气。

### 3.4 案例

- **只记发生过的事实**：发生了什么 → 代价 → 正确做法。
- **分正例和反例**：正例是做对了、值得重复的；反例是做错了、要避免的。这是必选的两种类型。
- **标签系统**：正例、反例之外，案例可以带其他标签，用于检索与总结。具体有哪些标签随实践补充，协议现在不规定词表。
- **编号**：每条一个编号（如 `C159`），编号是引用锚点。
- **按日期分文件**：`cases/<日期>.md`，只追加，不改写历史。
- **案例在发生的那一层**：发生在某个 Task 里的，写在该 Task 的 `cases/`；可复用的结论提炼进规范或飞轮（§11），案例本身不搬家。

### 3.5 工具

- **工具目录是 `tools/`**，每层都可以有。
- **一个工具一个子目录**，子目录里有说明书（`AGENTS.md`）和实现。说明书写清楚：做什么、什么时候用、输入输出、有什么副作用。
- **工具放在它的归属层**：跟某个 Agent 强相关、写死在代码里的，放在该 Agent × project 层的 `tools/` 下；跨项目通用的放在对应的上层。
- **工具可以读，也可以写**。协议不限制工具的来源，也不规定只能注册给某个运行时。
- **注册**：天生需要的工具可以注册给运行时（如 Pi），让模型直接调用；不需要的可以只放在 `tools/` 里，由 Agent 按说明书使用。两种方式都允许。
- **Agent 对用户的回应**：用户问"你有什么能力"时，Agent 可以指向相应层的 `tools/` 索引，说明有哪些工具、怎么用。

### 3.6 知识库

- **存放可复用的领域知识**，每条带出处（来源 + 日期）和失效条件。
- **知识库就是文档**：一个目录，里面按主题放文档，加上它的说明文件（`AGENTS.md`）。
- **按主题分**，不按时间分。

### 3.7 任务与任务类型

**任务**是有目标、需要落盘、需要可追溯的工作单元。

**任务是交互的粒度**：Agent 与用户的每次交互都落在某个 Task 下。Task 承载：

| 承载什么 | 落在哪 |
|---|---|
| 目标与背景 | 该 Task 的背景文档（类型模板决定叫什么、有哪些） |
| 执行步骤与每步的规范、目的 | 该 Task 的计划文档（模板决定） |
| 过程与重要事项 | 日志（§3.8） |
| 沉淀：案例、飞轮、规范、工具、知识 | 该 Task 对应的目录 |
| 状态：做到哪一步、是否完成、下一步是什么 | `task.md`（整体状态） |

**Task 的类型**（写在 `task.md` 的 `类型` 字段里）：类型是一个**可以扩展的集合**，每个类型对应 `task-types/<类型>/` 下的一份模板（`template.json`）和一份规则（`AGENTS.md`）。当前已有：

| 类型 | 取值 | 说明 |
|---|---|---|
| 日常 | `daily` | 系统保留：默认 Task 属于这个类型，承载日常对话的沉淀，按天分片（§6.1）。用户和 Agent 不手动新建 |
| 开发 | `development` | 开发、协作、结论类工作；类别见模板（当前 A / B / C） |
| 普通 | `general` | 不改产品行为、也不改协作规范的普通工作；类别 G |
| 问题定位修复 | `troubleshooting` | 独立类型：从具体现象出发，收集日志/现场/代码事实，以功能预期 + 代码事实 + 行业参考 客观定位根因，再修/转需求；类别 A / B / C（见类型规则） |

**新类型怎么来**：没有合适的类型时，Agent 与用户讨论，然后在 `task-types/<新类型>/` 下建模板与规则。类型的划分不是协议写死的，由实际工作决定。

**类别**由该类型的模板定义，协议不设统一的判据表：每个类型自己声明有哪些类别、各自需要哪些文件。Agent 选类别时，依据的是类型规则里的说明与当前工作的实际情况，必要时与用户确认。

**类型模板决定文件与规则**：每种类型的模板声明它有哪些文件（如开发类有 `log.md`，日常类有 `daily/`），并附一份类型规则（`task-types/<类型>/AGENTS.md`）。Task 的骨架一致，具体文件与规则由类型决定。

**类型可以要求过程记录与证据**：例如问题定位类（`troubleshooting`）要求 `log.md` 记录定位过程（假设→验证→结果→结论）、`evidence/` 保存过程证据（日志摘录、命令输出、截图、链接，写清来源与时间），并在背景文档中点名引用。协议只要求"过程可复核"；证据的形态与目录由类型规则定义。

**Task ID**：

- **格式**：项目内连续编号，四位，不复用，如 `0001`。
- **目录名**：`NNNN-标题`，如 `0001-default`、`0002-输入框优化`。
- **标题可以改，ID 不变**。所有引用都用 ID。
- **`task.md` 写 `ID: NNNN`**。
- **会话的 `activeTaskId` 存 ID**（§7）。

**状态**：`task.md` 是这个 Task 的整体状态源，写清楚：当前状态（进行中 / 暂停 / 已完成）、已完成到哪一步、剩余哪些步骤、下一步是什么、卡在哪。状态只在这里维护，其他地方只引用。

**任务模板的选择**（不合并）：按顺序找到第一份就用它：

1. 该 Agent × project 的 `task-types/<类型>/`；
2. 共享 project 的 `task-types/<类型>/`；
3. 协议默认的 `interaction-harness/task-types/<类型>/`。

模板必须能给出：类型与类别、必需文件清单、`task.md` 骨架、每个步骤的规范与目的、验收口径。模板的具体内容随落地迭代，协议只规定它存在、怎么选择。

### 3.8 日志

- **日志是过程性记录**：做了什么、为什么、发生了什么、哪些事情要记下来。它记的是事实经过，不是经验。
- **只追加，不改写历史**。
- **日志随 Task 走**：有日志的类型，日志在该 Task 下。
  - 开发类等普通 Task：`log.md`，记过程与重要事项；
  - 日常 Task：`daily/<日期>.md`，按天分片（§6.1）。
- **与飞轮的区别**：飞轮是持续积累的经验，日志是这一件事的经过。日志不是飞轮，也不替代飞轮。
- **日志不搬家**：日志留在它发生的 Task，只有从它提炼出的规范、飞轮、案例可以移动。

### 3.9 待办

- **一句话级的待办**，放在 `todo/`，每一层都有。
- **不是任务**：没有目录、没有类型与模板。
- **升级为任务时**：建一个 Task，把待办内容写进它的背景文档，然后从 `todo/` 删除该条。

### 3.10 会话与轮次

- **会话**：一次连续的对话，原始记录为 Pi 原生的 JSONL 文件。会话属于 Agent × project。
- **轮次**：一次用户输入加一次 Agent 回复（一次运行）。会话由轮次组成。
- **会话与轮次的原始记录不是日志，也不是沉淀**。沉淀进入日志、案例、飞轮、规范等对应的层。
- **会话通过 `activeTaskId` 引用 Task**：这是指针，不是绑定。同一个 Task 可以被多个会话引用，会话可以切换 Task。
- **每轮开始时读取指针**：指针决定这一轮写到哪里、按哪个 Task 的说明办事（§7）。

### 3.11 记忆（Agent 的能力）

**记忆是 Agent 的一项能力**。它分成几层，写在哪一层，取决于这条事实属于谁。协议规定层次、数据关系和用法；三个记忆工具的实现属于落地层。

| 记忆 | 归属 | 存放位置（所在层） | 谁能读 |
|---|---|---|---|
| 项目共享记忆 | 项目 | 共享 project 的 `memory/` | 绑定该项目的所有 Agent |
| 用户记忆 | 用户 | 用户层（跨项目、跨 Agent） | 该用户的所有 Agent、所有项目 |
| Agent 记忆 | Agent 本身 | Agent 本身的 `memory/` | 只有该 Agent |
| Agent 的项目记忆 | Agent × project | Agent × project 的 `memory/` | 只有该 Agent，且只在该项目内 |

**用法（协议要求）**：

- **读取顺序**：Agent 的项目记忆 → 项目共享记忆 → Agent 记忆 → 用户记忆。
- **默认只搜当前项目**。跨项目读取只能在用户明确要求时进行，并注明来源。
- **写入要按用户的指示**：不把每段对话都自动记下来。不确定记到哪一层，就问用户。
- **不自动共享、不自动提升**：写入项目共享记忆必须是用户明确指示。
- **不写敏感信息**（密钥、密码、Token、Cookie）；不写指令性内容（防注入）。
- **删除只在用户明确要求时进行**。批量删除先列出条目与数量，确认后再删。
- **记忆不覆盖当前指令**：当前请求永远优先。

**三个操作**：查、增、删。没有编辑。写错了就删掉旧条目，重新写一条。

## 4 层级与作用域

### 4.1 Agent 本身

Agent 本身是 `agents/<id>/` 根目录下的配置与能力，**不属于协作层级**：

- `agent.json`：身份与默认值；
- `identity.md`：身份正文；
- `tools/`：该 Agent 独有的工具；
- `memory/`：Agent 记忆（§3.11）。

**Agent 本身不设飞轮和案例**。它的经验与案例放在它的默认 workspace 下（§4.4）。

### 4.2 协作层级

| 层 | 位置 | 谁共享 |
|---|---|---|
| 共享 workspace | `~/.lifeos/projects/workspace/` | 所有 Agent |
| 共享 project | `~/.lifeos/projects/<pid>/` | 绑定该项目的所有 Agent |
| Agent × project | `~/.lifeos/agents/<id>/projects/<pid>/` | 只属于该 Agent（默认项目即 `workspace`，§4.4） |
| Task | Agent × project 下的 `tasks/<NNNN>-<标题>/` | 属于该 Agent × project |
| 会话 | Agent × project 下的 `sessions/` | 属于该 Agent × project |
| 轮次 | 会话内的一次运行 | 属于该会话 |

会话与轮次是对话记录，不携带规范，只携带指针（§3.10）。

**作用域**就是"谁必须遵守"：上表中的每一层，都是它下面内容的作用域。

### 4.3 加载顺序

加载规范时，按下面的顺序**逐层追加，不覆盖**：

```text
Agent 本身
  → 共享 workspace
  → 共享 project
  → Agent × project
  → Task（当前指针指向的 Task）
```

- **私有优先**：先加载 Agent 自己的东西，再加载共享的东西。
- **只加载当前会话可见的层**；不扫描其他项目，不扫描其他 Task。
- **同一份正文只加载一次**，重复路径去重。
- **冲突不自动覆盖**：停下，指出冲突的层，由用户裁决或修改原文件。
- **顺序只决定阅读次序**，不决定谁覆盖谁。
- **每个加载的文件记录来源路径**；没有来源的内容不能当成规范。

### 4.4 workspace（默认项目）

- **共享 workspace**（`~/.lifeos/projects/workspace/`）：所有 Agent 共享的特殊层。它的结构与共享 project 相同，即它是一个 `id` 为 `workspace` 的共享项目。
- **Agent 的默认 workspace**（`agents/<id>/projects/workspace/`）：Agent × project 的一个实例。**当用户还没有添加任何项目时，交互就在这里进行。**
- **两个 workspace 同名、不同层**：前者是所有 Agent 的共享项目，后者是该 Agent 的默认项目。
- **默认 workspace 与其他项目的结构完全相同**。飞轮、概念空间、案例、规范、工具、知识库、待办、默认 Task，都在它下面。Agent 跨项目的经验也放在这里（§3.1）。

## 5 结构与说明文件

### 5.1 每层的目录结构

所有协作层的结构相同：

```text
<层>/
  AGENTS.md          说明文件：背景与目的 · 内容 · 何时读 · 怎么用（§5.2）
  concept-space.md   概念空间（§3.2）
  flywheel.md        飞轮（§3.1）
  specs/             规范（按主题分目录；index.json 为机器索引）
  cases/             案例（按日期分文件，§3.4）
  knowledge/         知识库（按主题分，§3.6）
  tools/             工具（一个工具一个目录，§3.5）
  todo/              待办（§3.9）
  task-types/        任务类型模板（只有能选任务类型的层有，§3.7）
  memory/            记忆（只有有记忆的层有，§3.11）
  project.json       项目身份（只在共享 project 层有；§5.3）
  sessions/          会话（只在 Agent × project 层有）
  tasks/             任务（只在 Agent × project 层有）
```

**Task 的结构**（同样的骨架，文件由类型决定）：

```text
tasks/<NNNN>-<标题>/
  AGENTS.md          说明文件
  task.md            整体状态与指针（§3.7）
  concept-space.md   概念空间
  flywheel.md        飞轮
  specs/             规范
  cases/             案例
  knowledge/         知识库
  tools/             工具
  todo/              待办
  log.md 或 daily/   日志（由类型决定，§3.8）
```

**Agent 本身的结构**：

```text
agents/<id>/
  AGENTS.md          说明文件
  agent.json         身份与默认值
  identity.md        身份正文
  tools/             该 Agent 独有的工具
  memory/            Agent 记忆
  projects/<pid>/    各项目的空间（§5.2）
```

**协议目录**（协议自己的位置，不属于任何协作层）：

```text
interaction-harness/
  AGENTS.md          协议目录的说明
  protocol.md        本协议正文
  skeleton/          目录说明文件（AGENTS.md）的模板：每个目录的说明都从这里取文字
  task-types/        协议默认的任务类型模板
```

### 5.2 说明文件

- **每个目录都有一份说明文件，统一叫 `AGENTS.md`。**
- **建目录即写说明**：创建或补齐任何目录的同一个动作，必须同时写它的说明文件；"目录在、说明不在"是不符合本协议的状态，由结构校验判定。
- **说明文字的来源**：通用目录说明以协议目录的 `skeleton/` 为唯一事实源（骨架与代码只负责复制与补齐，不另写文字）；目录自己的具体内容说明，由该目录自行撰写与维护。
- **说明文件写四件事**：① 背景与目的（这个目录为什么存在）；② 里面有什么；③ 什么时候读；④ 怎么用（读写的规则）。它不记过程，不复制协议正文。四件事的内容质量靠检视核对，机器只判定"存在与伴生"。
- **说明文件承载内容要求**：该目录的产物必须包含什么（如：案例的背景与正/反/标签、计划的动作/契约/目的/测试/对照检查、规范条文诞处的检查方式），也是说明文件的一部分；**内容要求的唯一事实源是协议目录的 `skeleton/`**——目录创建时由骨架生成，新任务/新项目里将来创建同类目录时自然继承，不做逐任务复制。
- **分两层说明**：外层说明列出下层有哪些子目录/文件、各自是什么；目录内的说明文件写这个目录本身。
- **目录名加说明文件才是契约**。只靠目录名，Agent 无法知道里面有什么。

### 5.3 项目身份

- **`project.json` 只放在共享 project 层**（`~/.lifeos/projects/<pid>/`），是这个项目的唯一身份。
- Agent × project 层不再放 `project.json`，它通过 `pid` 绑定到共享 project。
- 外部项目的目录路径（`path`）写在共享 project 的 `project.json` 里。
- 共享 workspace 的 `project.json` 只有 `id` 与名称，没有 `path`。

## 6 Task：默认 Task、日常 Task 与普通 Task

### 6.1 默认 Task（日常）

- **每个 Agent × project 一个**，目录名 `NNNN-default`（通常是 `0001-default`），类型 `daily`。
- **承载日常对话**：用户还没有想好要创建什么 Task，或做什么 Task 时，随意的交互都归到默认 Task。
- **按天分片**：当天的沉淀写进 `daily/<日期>.md`。这是这一天的日常会话沉淀，不是原始对话。
  - **什么时候建**：发起对话（每轮交互）时，按本地日期建当天的分片；没有交互的日子没有分片。一周没有会话，就没有这一周的文件。
  - **写什么**：当天对话中值得留下的结论、决定、待办、案例线索、可复用的经验线索。
  - **不写什么**：原始对话（它在会话记录里）、与其他 Task 的具体工作（它们进各自的 Task）。
- **天数多了以后按月分组**。什么时候切换由默认 Task 的 `AGENTS.md` 规定，协议现在不规定触发条件。
- **长期存在**：不完成，也不删除。
- **跨天不换指针**：一个会话跨午夜，轮次写进新一天的分片，会话仍指向默认 Task。

### 6.2 普通 Task

- **用户下达的工作**：由用户在对话中发起，有目标，可能跨多轮。
- **有类型与类别**，决定使用哪份任务类型模板（§3.7）。
- **有日志**：开发类等类型的 `log.md`（§3.8）。
- **状态是记录，不是锁**：可以标为已完成，之后用户再问，随时改回进行中；Task 目录不删除，除非用户明确要求。
- **Agent 定时任务**是另一类，按时间或事件触发，反复运行；它的规则在定时任务功能落地时再写入协议（§13）。

### 6.3 日期

- **Task 目录平铺**，不按日期建物理目录。
- **日期写在字段里**：`task.md` 的 `日期：YYYY-MM-DD`；界面按日期分组。

## 7 会话、指针与历史

- **会话属于 Agent × project**，通过 `activeTaskId` 指向一个 Task。
- **进入 Task 即切换**：用户进入某个 Task（界面里选择，或 Agent 在对话里建了它），会话指针就指向它；下一轮装配读取新指针，当前正在进行的轮次不换上下文。不设单独的"切换工具"。
- **每轮开始读取指针**，只加载当前 Task 的说明与状态：
  - 当前 Task 的 `AGENTS.md`；
  - 当前 Task 的 `task.md`；
  - 当前 Task 类型的规则 `task-types/<类型>/AGENTS.md`（选择顺序见 §3.7）。
- **不自动加载其他 Task 的内容**。Task 内其他文件，由 `AGENTS.md` 的索引指引，Agent 按需读取。
- **会话的历史可以删除、改写**（用户的动态编辑）。
- **沉淀先于删除**：删除历史前，需要保留的内容必须已经写进对应的层（日志、案例、待办、知识、飞轮、规范）。这些内容只追加，不随会话历史删除。
- **Task 的指针不随历史删除而改变**：删除会话历史不改变 Task 的状态与内容。

## 8 默认会话

- **默认会话**：随模板出厂预置的第一条会话，只随 Life OS 的默认 Agent 装入。
- **第一句是 Agent 打招呼与说明书**：用户打开系统时，Agent 先告诉用户可以怎么用，用户顺着对话就会用。
- **第一句不是模型输出，也不是用户消息**：它是预置的记录。模型的第一次推理由用户对它的回复触发。
- **文件驱动**：预置文件是普通会话，加载即显示，没有特殊样式。
- **用户删除后不复活**：删除后新建的会话是空白会话。
- **显示名**：预置文件里写明会话名称，用户可以改名覆盖。

## 9 加载与装配（协议层的约束）

- **常驻**：协议正文，以及协议目录的说明。
- **按顺序加载规范**：§4.3 的顺序，逐层追加；**各层的规范全部加载，不按场景筛选**（协议不设场景机制）。
- **当前 Task**：指针指向的 Task 的说明、状态与类型规则（§7）。
- **项目仓库的说明**：外部项目的仓库根目录里的 `AGENTS.md` 作为项目规范单独读取（只读这一份，不继承父目录）。
- **说明文件索引**：每层说明文件的索引（只列有什么、在哪），不注入正文。这样 Agent 知道去哪里找。
- **按需读取**：飞轮、案例、知识、工具的正文，由索引指引，Agent 用读取动作获取。
- **不跨项目**：当前项目之外的内容不扫描、不注入。
- **不扫描其他 Task**：只加载指针指向的那一个。
- **可反查**：每个加载的文件记录来源路径。
- **每轮重新装配**：每次运行前，按会话的当前指针重新读取上面的内容。系统提示里的"当前 Task"因此每轮替换，不会累积上一个 Task 的内容。
- **对话历史不替换**：之前轮次的消息、以及 Agent 当时读过的文件内容（工具结果），仍在对话历史里。历史的清理属于用户的动态编辑（§7），不由装配完成。

## 10 存储策略（按什么切分）

| 内容 | 按什么分 | 理由 | 索引 |
|---|---|---|---|
| 案例 | 按日期（一天一文件） | 事实按时间发生，只追加 | 需要（编号 + 日期 + 一句话） |
| 日志（日常 Task） | 按日期（`daily/<日期>.md`） | 日常对话按天累积 | 不需要（按天查） |
| 规范 | 按主题 | 会被改写与取代，不是流水 | 需要（`specs/index.json`） |
| 概念空间 | 一份文档 | 词不多，一份即可导航 | 文档内目录 |
| 飞轮 | 一份文档 | 经验是一份持续更新的文档 | 不需要 |
| 知识库 | 按主题 | 查阅按主题 | 需要（主题索引） |
| 工具 | 一个工具一个目录 | 工具按功能用，不按时间累积 | 需要（说明文件列出） |
| 待办 | 一句话一条 | 清单 | 不需要 |
| Task | 一个 Task 一个目录 | 工作单元 | 不需要 |

**共同要求**：凡"按主题、按功能"的都要有索引；凡"按日期"的都要有编号或日期，便于引用。

## 11 维护与提升

| 规则 | 内容 |
|---|---|
| 分级维护 | 谁的内容谁维护：Task 内容改 Task 目录；项目内容改项目层；跨项目内容改 Agent 的默认 workspace；所有 Agent 的内容改共享 workspace |
| 提升 | 低层内容在别处也用得上，可以提升到任何更高的层。移动正文，原处只留一行指针，不复制 |
| 判断提升到哪一层 | 看谁必须遵守：只有当前 Task 用 → 留 Task；同一项目的 Task 都用 → 项目层；同一 Agent 跨项目用 → Agent 的默认 workspace；所有 Agent 用 → 共享 workspace |
| 不复制 | 同一件事只有一处正文；跨层引用写链接与编号 |
| 历史不改写 | 案例与日志只追加；被取代的规范标注取代关系，不删除推理链 |
| 案例与日志不搬家 | 案例、日志、待办留在发生的层；只有从它们提炼出的规范、飞轮可以提升 |
| 模板是选择，不是叠加 | 任务模板按 §3.7 选一份；规范是逐层追加 |

## 12 动作与落点（协议层）

| 动作 | 落点 |
|---|---|
| 读取案例、概念、知识、规范、飞轮正文 | 按索引找到路径，用读取动作获取 |
| 记录当天的日常沉淀 | 默认 Task 的 `daily/<日期>.md` |
| 记录普通 Task 的过程与重要事项 | 该 Task 的 `log.md` |
| 登记一句话待办 | 所在层的 `todo/` |
| 沉淀案例 | 发生的 Task 的 `cases/`（按日期） |
| 沉淀飞轮、规范、工具、知识 | 按 §3.1、§11 的判据，放在对应的层 |
| 切换 Task | 改会话的指针，下一轮生效 |
| 新建 Task | 按类型模板建目录与 `task.md`，编号连续 |
| 使用记忆 | 按 §3.11 的用法，用记忆工具查、增、删 |

工具本体、模板的具体内容、加载器的实现，属于落地层，不在本协议中规定。

## 13 待定（随落地与实践迭代）

1. **默认 Task 按月分组的触发条件**：由默认 Task 的 `AGENTS.md` 规定，天数多了再定。
2. **日常分片的内容格式细则**：随第一批实践定。
3. **案例标签的词表**：正例、反例之外，具体标签随实践补充。
4. **任务类型**：目前只有开发类与普通类，其他类型按需补齐。
5. **Agent 定时任务**：调度、运行记录、运行产出的结构，随定时任务功能落地时写入协议。
6. **日记**：等定时任务功能再规划。
7. **既有架构文档的转化**：架构与模块文档转为知识库条目，开发规范转为规范，案例与日志按日期。转化只改组织方式，内容仍需逐份核对。
8. **飞轮的装配方式**：目前按需读取，是否要在装配时注入正文，待实践后决定。
