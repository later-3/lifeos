# 多 Agent 协作规范（共享 workspace）

> 角色：架构 / 开发　类型：规范　状态：**现行**（2026-10-22）
> 适用：所有 Agent、所有项目；只约束“什么时候把工作交给另一个 Agent/会话”，不规定具体产品实现。

## 1. 先判断是否真的需要协作

默认由**主 Agent 单线完成**。只有同时满足以下条件才委派：

1. 子任务边界清楚，有独立输入与可验收输出；
2. 子任务能隔离上下文（不需要主 Agent 的全部隐式知识）；
3. 主 Agent 有时间和能力复核结果；
4. 失败可以回退，不会把未经验证的改动直接交付。

以下情况**禁止**用子 Agent 掩盖问题：需求本身不清楚、需要用户拍板、涉及凭据/权限/部署、只是为了“看起来并行”。

## 2. 角色与责任

- **主 Agent**：对用户负责；拆解、给边界、监督、验证、采用/拒绝、最终交付。
- **子 Agent**：只对**被交付的边界**负责；输出是候选，不是结论；不得自行扩大范围。
- **用户**：保留最终决定权；涉及取舍、风险、不可逆操作时必须回到用户。

## 3. 子 Agent（subagent / delegate）

必须给出完整交接（见 §6），并遵守：

- 一个工作区同时只有一个写者；并行写必须各自独立 worktree；
- 子 Agent 不自动提交、不合并、不推送、不部署；
- 子 Agent 不得读取或输出凭据；不得修改父会话/其他 Agent 的私有数据；
- 主 Agent 必须检查：改动范围、测试/证据、是否越界、是否满足验收；
- 子 Agent 失败时停止并报告，不静默切换模型/工具或伪造结果。

## 4. 会话分叉（fork / clone / tree）

- **fork**：从当前上下文分出一条替代探索；分叉后各自独立，不共享可变状态；
- **clone**：复制一份会话继续，原会话不被改写；
- **tree**：只用于浏览谱系，不代表已合并；
- 分叉结果只有经过主 Agent 对比、验证并由用户确认后才进入主线；
- 不把 fork 当成“自动并行”，也不默认合并所有分支。

## 5. 群聊 / 多 Agent 房间

当前**没有**成熟的群聊实现可直接移植；不要把“多 Agent 同时说话”当成默认能力。

若未来引入，必须先定义：房间与成员、消息发送者身份、共享游标、轮次上限、谁可以终止、失败如何隔离、哪些内容可被所有成员读取。没有这些定义不实现群聊。

## 6. 交接（handoff）必须包含

1. **任务**：要做什么、不要做什么；
2. **范围**：允许读/写的目录、文件、分支/worktree；
3. **约束**：规范、验收标准、时间/预算；
4. **证据**：相关文件、复现步骤、已知失败；
5. **输出**：交付格式、存放位置、如何验证；
6. **状态**：已完成/未完成/阻塞点，方便下一个 Agent 接着做。

口头或一句“你去做 X”不构成可执行交接。

## 7. 工作流（workflow）

脚本化多子任务只用于**可重复、边界稳定**的流程：

- 先写清每个节点的输入/输出与失败处理；
- 不把用户交互、凭据、不可逆操作放进自动链路；
- 汇总结果由主 Agent 复核，不自动采用；
- 流程变化时改原流程，不复制一份平行版本。

## 8. 禁止项（可检查）

- 子 Agent 越界写父工作区 / 其他 worktree；
- 未定义验收就宣称完成；
- 子 Agent 输出直接作为最终交付；
- 把凭据、Token、Cookie、私钥放进交接或日志；
- 无上限地递归委派或群聊刷轮次；
- 用分叉/并行绕过用户对范围或风险的确认。
