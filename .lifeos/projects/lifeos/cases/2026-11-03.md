## C162（反例）用户选了 amr-link，实际请求跑到 DeepSeek 官方并 402 —— "界面上的模型"与"真正发出去的模型"分叉
标签：反例 · 模型选择 · 凭据 · 静默降级 · 用户报告 · Task 0017

### 现象（用户 2026-11-03）

用户在 `127.0.0.1:43120` 打开两个会话（`01a19c1b-bee4-73c9-abbe-fa2cc599f106`、`01a19770-9d9d-77b3-8259-16b54cd4b4ff`），界面**顶部显示 amr-link/deepseek-v4.1-flash**（用户自己的选择），但发消息报：

```
模型调用失败 20:10
402: {"message":"Insufficient Balance (request_id: 651001a5-…)",
      "type":"insufficient_balance_error","code":"invalid_request_error"}
```

用户第一反应："是不是上下文太大了？需要新 session 了？" —— 都不是。用户第二反应："我选的是 amr-link，如果它用不了应该直接报错，静默换别的模型非常危险。" —— **这一句是对的**。

### 事实链（每条都实测过）

| # | 事实 | 证据 |
|---|---|---|
| 1 | 会话文件里最后一条 `model_change` 仍是 `amr-link/deepseek-v4.1-flash`，但 assistant 消息全是 `provider:"deepseek", model:"deepseek-v4-pro"` | 两个会话 JSONL |
| 2 | 运行态 `meta.model` = `deepseek/deepseek-v4-pro`，而 `GET /config` 的 `effective` = `amr-link/deepseek-v4.1-flash` | 接口实测 |
| 3 | 前端按 `modelOverridden === false` 显示"Agent 有效默认"（= amr-link），不是实际模型 | `frontend/src/App.tsx:1976` |
| 4 | 后端进程 `PID 19139` 环境里**没有** `AMR_LINK_API_KEY`；它祖父 zsh 起于 10-29 12:19，而 `~/.zshrc` 里那行是 10-31 18:06 才写 | `ps eww` |
| 5 | `models.json` 里 amr-link 的 key 是引用式 `"${AMR_LINK_API_KEY}"`；变量缺失 ⇒ `hasConfiguredAuth("amr-link") === false` | `ModelRuntime` 实测 |
| 6 | 时间线吻合：19:45 最后一次 amr-link 成功 → **19:48 进程重启** → 19:56 起全部 deepseek-v4-pro | 后端日志 |
| 7 | DeepSeek 官方余额：`-0.52` 元，`is_available: false` | `/user/balance` 实测 |

### 根因（两层，缺一都不会出事）

**根因 A · 上游静默默认（Pi 行为）**

`pi/packages/coding-agent/src/core/sdk.ts:224-249`：恢复会话时如果 `hasConfiguredAuth(该 provider) === false`，就设 `modelFallbackMessage` 字符串，然后走 `findInitialModel()` **按 `defaultModelPerProvider` 顺序挑一个"有凭据的任意模型"**。`model-resolver.ts:29` 里写着 `deepseek: "deepseek-v4-pro"`，而 `LIFEOS_KEY_DEEPSEEK` 在进程里 → 选中 DeepSeek 官方。它只给了一个字符串，**Life OS 从来没读过它**。

**根因 B · 我们自己从来没看过实际模型（本次真正的 bug）**

`src/agent-host.ts` 的 `adoptAgentDefault` 只在 `decideRestoreModel(...) === "follow"` 时调 `setModel`。而这个纯函数比较的是**两个记录值**：

```
会话文件里的 model_change： amr-link/deepseek-v4.1-flash
Agent 默认：              amr-link/deepseek-v4.1-flash
→ 相同 → 判 "keep" → 不调 setModel → 什么都不做
→ 但 Pi 已经把 session.model 换成了 deepseek-v4-pro
→ 没有任何一行代码检查 session.model
```

**所以根因不是"少了一个校验"，是"从来没看过实际模型"。** 说"界面显示错了"也不对——界面忠实显示了配置，是**配置与实际已经分叉**而无人发现。

### 代价

- 用户在**不知情**的情况下把请求打到另一个付费服务商，直到对方欠费（-0.52 元）才暴露。这是一条**会静默花钱**的路径，不是纯显示问题。
- 排查绕了三个弯：先怀疑上下文超限（确实有一次真的 `400 maximum context length`，但 12:00 已自动 compact 成功，之后的 402 与它无关）；再怀疑 session 太老；最后才发现是进程环境缺变量。
- **`pnpm test:ui` 里本来就有一条测试在报这个 bug**：`头部显示会话实际模型（与接口 meta 一致）` → `头部 amr-link/… ≠ 接口 deepseek/…`。它一直在报警，没人看。而紧挨着的另一条 `未覆盖会话头部显示有效默认（不显示会话实际值）`**把 bug 的行为写成了期望**——测试既报警又掩护。

### 正确做法

1. **模型是契约，不是提示**：用户选了什么，实际就必须是什么。决定"期望模型"之后要**校验实际**（`session.model === expected`），不等就切回，切不回就报错。
2. **四条路径都要管**：新建会话 / 恢复会话 / 发送消息 / 切模型。只在其中一条上做校验等于没做。
3. **凭据预检用实时接口**：`checkAuth()`（每次现读 `process.env`，实测 0.008ms），**不能**用 `hasConfiguredAuth()`（`ModelRuntime.snapshot` 缓存，写 env 后仍返回 `false`）。Pi 的 `setModel()` 内部用的正是 `checkAuth`，所以"切模型"这条路天然正确。
4. **错误必须说到变量级**：不是"模型调用失败"，而是"缺少环境变量 `AMR_LINK_API_KEY`"。并且要分三种病：`missing`（不存在）/ `empty`（存在但空白，Pi 的 `value.trim().length > 0` 判为没有）/ `malformed`（带引号或空格，Pi 判为有但发出去 401）。
5. **界面显示实际运行模型**，不是配置值。两者不一致时该被看见，不该被掩盖。
6. **环境变量是进程私有的**：父进程 `export` 过才有，别处的 `export` 接不到（`source` 也只对那个 shell 生效）。要"不重启也生效"只能自己去读 shell 配置文件；做不到的情况（只在某终端 export 过 / 需要 `$(…)` 求值）要**明说让用户重启**，不能假装能解决。

### 对应实现

`src/agent-host.ts`（四条路径 + `describeModelUnavailable`）· `src/env-refs.ts`（从 `"${VAR}"` 解析变量名 + 判三种病）· `src/env-reload.ts`（静态读 shell 配置补 `process.env`，0.010–0.035ms；`zsh -ic` 重跑是 7.5s/次且执行用户全部 shell 副作用，禁做）· `src/failure.ts`（新增 `model_not_configured`）· `frontend/src/App.tsx`（头部恒显示 `meta.model`）· `frontend/test/ui-contract.mjs`（反转旧契约 + 新增"未覆盖但被换掉→显示实际"）。
