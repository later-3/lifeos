## C163（反例）输入框 ↑ 取回的是"整页一份、方向反、只能走一步"的历史 —— 四个缺陷叠在一起，而门禁一直全绿
标签：反例 · 前端 · 输入框 · 状态归属 · 契约测试假绿 · 用户报告 · Task 0012

### 现象（用户 2026-11-05）

> 我们的输入框，按键盘的上键，期望是历史消息，现在是乱的，这个历史消息是针对每个 session 单独来说的。

拆成三条预期：① 空输入 ↑ 取回**本会话**发过的消息；② 按 session 隔离，切会话/切 Agent 不串；③ 顺序正确，最近一条先出。

### 代价

- **用户能感知的错乱持续了很久**，而 `pnpm test:ui` 里那条「空输入 ↑ 取回输入历史」**一直是绿的**。
- 定位花了大半天，因为"乱"是四条不同缺陷的合成症状，只修一条（方向）用户仍然会觉得乱——如果按"用户说方向反了"直接改 `delta` 的符号，会得到一个**看起来修好了、其实还有三个**假修复。
- 假绿的根因值得单独记：断言只发了**一条**消息、只按了**一次** ↑。这个形状恰好让四个缺陷全部不触发。

### 根因

**错在模型，不在某一行。** 老实现把"输入历史"当成一份**独立的内存流水**：发送时自己往数组里塞，因此必须自己负责"按会话分开"和"正确导航"——两件都需要"记得"的事，结果一件都没做（没清、没算对方向）。

四条缺陷都是这个模型的必然产物：

- 因为要自记 → 就得记得清（漏了）；
- 因为数组能自由选择追加方向 → 追加用旧→新、读取用新→旧，两处口径不一致（反了）；
- 因为"是否在浏览"没有独立状态、只能借 `input === ""` 兼职判断 → 取回后条件不成立（走不动）；
- 因为游标是裸下标、没有作用域 → 换了会话或清了输入框，下标仍然是旧的（错位）。

同一时间 Pi SDK 早就把「当前会话的用户消息」送到前端了（`messagesOf()` → `GET /api/agents/:id/sessions/:sessionId`），前端却在旁边自己记第二份。

### 正确做法

1. **会话级输入状态优先派生，不自记**：`inputHistoryOf(messages)` —— 事实源只有一个（服务端会话消息），切会话天然隔离、刷新不丢，不需要在任何"切换"路径上补清理代码。
2. **必须记的状态要带作用域**：游标 = `{ index, scope }`，`scope !== 当前作用域` 就视作未在浏览。这样切换不需要清理，游标自己失效。
3. **"空输入"只是进入浏览的条件，不是每次按键的前提**（Pi TUI `editor.ts:926-930`：`isEditorEmpty() || historyIndex > -1`）。
4. **用户一打字就退出浏览**（Pi TUI 每个编辑动作都调 `exitHistoryBrowsing()`），且判定靠 textarea 的 `onChange`（只有用户输入会触发），不靠"文字是否等于历史某条"猜。
5. **契约断言要覆盖会触发缺陷的形态**：多条历史 + 两个会话 + 连按 ↑↓ + 真点击会话行切换。并且做一次红→绿活性验证：把实现还原成旧版，新断言必须转红。

### 复用的判断信号

- 一个"看起来是某一条规则错了"的用户反馈，往往意味着**背后的模型错了**；只改那一行会得到假修复。
- 只要一处状态需要"在切换时记得清"，就一定会有一个路径漏清。**能派生就不要自记**。
- 一条断言写成"一条数据 + 一次操作"时，问自己：实现全错的情况下，它还绿吗？如果绿，它什么都没测。
