# knowledge/design/im/ —— IM 版界面设计（v2 目标设计）

## 背景与目的

Life OS 前端正在换成"以 Agent 为中心"的 IM 架构（模型 B，见 `specs/frontend-mobile/mobile.md` §2）。
这组文档是**目标设计的唯一依据**：先立设计语言，再写页面设计，然后照着实现 demo。

**为什么单独一个目录**：这套设计先在 `demo/lifeos-im/`（独立静态打桩）里做出来给人看，
还没落到 `frontend/src`（主前端冻结中）。落地那一步是**取代**，不是"多一套"：
`design-language.md` 并入 `specs/frontend-development/frontend-spec.md` §2 与 `frontend/src/design/tokens.css`，
页面文档逐份取代 `knowledge/design/` 下同名的现行页面文档，然后本目录删除。
**在删掉之前，这两个地方描述的是同一批页面的两个版本 —— 以本目录为准（新版本），现行文档代表"现在线上什么样"。**

## 什么时候读

- 改 demo 或落码新前端：**先读 `design-language.md`**，再读要动的那个页面文档。
- 用户说"这里字小了 / 这段多余了 / 这里挤"：按下面的顺序走，**不许直接改数值**。
- 写新的页面：先在目录里加一份页面文档（照现有结构），再写代码。

## 用于改**真前端**时（顺序不能倒）

1. **先实测对照**：用 `tools/fe-compare-shot` 在 5174（开发实例）与 5173（用户实例）上，
   以**同一步骤序列**截同一块（三列区域用 `--clip 44,0,732,420`），再看**计算样式**
   （字号/字重/行高/颜色/尺寸）—— 不靠看图选数值；
2. **对照本文找到位置与数值**（层级 §5、间距 §2、颜色 §3、徒标与状态点 §5.2、图标 §5.3）；
3. 缺就**先补本文 + 决定编号（D…）**，再改 primitive / token，最后才改页面；
4. 每条视觉改动配一个可断言的检查（**计算样式断言优先**：截图基线会把行内容遮掉，
   对行内排版不可见 —— 案例 C152）。

**实测对照（2026-10-30，开发实例 5174）**：真前端三列列头**全为 11px/500**，三列行全为 13.5px
（二三级无层级）→ 已按 D9 先把第二级（项目行）升为 section。真前端头像底已是 token 的
`accent` / `ink-700` / `ink-900`（对比 **5.17 / 9.75 / 16.80**，均达标）—— 所以 §3.3 的头像底色决定
**只属于 demo**，不要在真前端重复合成。
证据：Task 0003 `assets/2026-10-30-P01-*`。

## 怎么用（反馈 → 规范 → 实现）

1. **定位区域**：这段话属于哪个区域？在该页面的"区域构成"表里找它的职责。
   - 表里没有这个区域 → 页面设计有缺口，先补表，再谈改。
   - 职责是"复述别处已有的事实" → 冗余在职责，改表达（或删区域），不是只删字。
2. **定位数值**：它用的是哪一档字号/哪个颜色角色？
   - 不在表里 → 说明实现漂了，先归位到档位。
   - 在表里但判断错了（如"分区标题用了 label 档"）→ 改 `design-language.md` 的决策记录（D 编号），
     再全站扫同类位置。
3. **改实现**：只改 token 或映射，不改散落的数值；改完跑 `node demo/lifeos-im/check.mjs`
   （字号/圆角/间距只认档位、文字对比度 ≥4.5、ink-300 不作文字）。
4. **回写**：决策进 `design-language.md` §7；页面级结论进对应页面文档；踩到的坑进 Task 的 `cases/`。

## 规则（必须）

- 同一事实只写一处：数值只在 `design-language.md`，页面文档只引用（写"content 档"而不是"15px"的地方可写推导，但不定义档位表）。
- 页面文档必须写"这一屏不负责什么" —— 没有这句，"冗余"就无法判断。
- 决策要带证据编号（D1、D2…）；没有证据的偏好写进"待验证"，不当规则。
- **数值不得凭记忆写**：本文经历过一次“旧一代盖掉新一代”的事故（C153），所以凡写入本文的数值必须
  带上实测戒参考出处；记忆里的旧表先当“待核对”，核对后才能写。
