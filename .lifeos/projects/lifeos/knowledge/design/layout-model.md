# 前端布局模型（统一路线）

> 角色：设计　类型：**架构约束**　状态：**v1（2026-11-09 用户确认参考清单后定稿）**
> 用户原话：「后面我们需要增加一些其他页面，我们也是有一个统一的一个路线，就是该怎么去切换，该怎么去展示，不可能是永远是乱的，比如说你看我的截图，为什么那里莫名其妙会有一个"返回对话"？所以呢，我们一定是要整体和局部再加细节要协调统一的。」

## 1 L1 整体：三层骨架（所有页面同一套）

```
┌────┬──────────────┬────────────────────────────┐
│ ①  │ ②            │ ③                          │
│rail│ 列表列        │ 内容区                      │
│44px│ 240–440 可拖  │ 剩余全部                    │
└────┴──────────────┴────────────────────────────┘
```

| 层 | 是什么 | 谁拥有它 | 规则 |
|---|---|---|---|
| **① rail** | **两类开关并存**：列开关 + 功能页 | 全局唯一，常驻 | ① **列开关**（`mode:"toggle"`）：助手 / 对话 —— 高亮 = 该列**已展开**（`aria-pressed`），点击 = 开/关该列；② **功能页**（`mode:"tab"`）：设置 —— 高亮 = 当前所在页（`aria-current="page"`）；③ 可分组（novu `NavigationGroup`）；④ 可带未读徽标（LobeHub `RailItem.badge`，边框式见 Hoppscotch） |
| **② 列表列** | **当前 tab 的列表** | 由 tab 决定 | 每个 tab 声明自己的列表；不限"助手列+会话列"这一种组合；宽度按 tab 记忆 |
| **③ 内容区** | 当前 tab 的主内容 | 由 tab 决定 | 一个 tab 只有一个内容区；**不再有跨 tab 的浮层堆叠** |

### 1.1 rail 的内容（v1，2026-11-09 用户二次裁决后定稿）

| 位置 | 项 | 类型 | 谁决定 ② / ③ |
|---|---|---|---|
| 业务组（上） | **助手** | **列开关** | 开/关"助手"列（该列是会话列的前置选择列） |
| 业务组（上） | **对话** | **列开关** | 开/关"会话"列（项目分组 → 会话行） |
| 底部（推底） | **设置** | **功能页** | ② = 设置分区；③ = 分区内容 |

**关键差异（本产品 ≠ LobeHub）**：Agent × Project × Session 是三级结构，**助手列与会话列是两个可各自收起的列**。
LobeHub 那种"每个 tab 一个列表"的单层模型会把这两列压成一个开关，**减少功能**。
所以 rail 必须同时支持"列开关"与"功能页"两种语义，用 `mode` 区分（`design/rail.tsx`）。

**未来的功能页**（项目 / 动态 / 笔记）按 `mode:"tab"` 加在业务组或内容组；
**不进 rail 的面**：Agent 主页、Task 详情、检视、用户主页——它们是**对象详情**，从列表点进去在 ③ 内以详情态出现（Twenty show-page 同构）。

### 1.2 硬规则（每条都可机器检查）

1. **新增页面必须先分类**：它是**列开关**、**功能页**，还是**对象详情**（在 ③ 内出现）？三类都不许混用同一种按钮语义。
2. **不许跨 tab 的浮层**：设置不能再"盖在对话上"——它就是 ②③ 的内容（用户 2026-11-09 截图里的「返回对话」按钮就是违反这条的症状）。
3. **切换 tab 不丢列表状态**：② 的滚动位置、展开状态**按 tab 持久**（不靠组件保活补丁）。
4. **两类高亮语义不许混**：列开关用 `aria-pressed`（= 该列展开），功能页用 `aria-current="page"`（= 当前所在页）。
5. **手机（<640）**：① 收进底部 tab 或抽屉；② 与 ③ 全屏互斥（drill-down），不同时出现。

## 2 L2 局部：每个面的骨架

| 面 | 骨架 | 依据 |
|---|---|---|
| **对话工作台** | ② = 助手（可折叠）→ 会话分组列表；③ = 头部（标题/元信息/右侧入口）+ 消息流 + composer | LobeHub `NavPanel` + 现有实现；会话行两行形态见 §2.1 |
| **设置** | ② = 分组导航（外观/显示/动效/语言/模型/通知/关于）；③ = 内容列 **760** 居中 + **一组一卡** | Twenty `SettingsContentMaxWidth.ts:1` + `SettingsPageContainer.tsx:39-41`；LibreChat 的项级 registry（§2.2） |
| **动态流** | ② = 类型过滤（带计数）；③ = 卡片流 | Misskey + IG/小红书（另一 Task） |
| **项目台 / Task** | ② = 列表；③ = 概览卡网格 / 详情块（有数据才渲染） | Plane |

### 2.1 会话行（对话工作台）

两行：**标题**（`body 13.5 / 600`）+ **元信息**（`micro 11`，参与者头像 16 + Task 编号 + 状态），右缘一个状态槽（运行/未读/失败/时间，四态互斥）。
依据：现有实现 + `#12 绿底三栏社交`（同构左列表：头像 + 名字 + 副标题 + 右缘图标）。

### 2.2 设置项（不是"分区里堆 HTML"，而是**项级数据**）

借 LibreChat `Nav/Settings/registry.tsx` + `types.ts`：

```ts
type SettingEntry = {
  id: string;            // 稳定 id（localStorage 键 / 测试选择器共用）
  section: SectionId;    // 分区
  label: string;
  keywords?: string[];   // 搜索用（LibreChat search.ts:1-20 的 normalize + keywords 匹配）
  show?: (ctx) => bool;  // 条件显示（我们用它把"未实现"的项直接不显示，而不是显示禁用控件）
  control: "slider" | "swatches" | "segmented" | "toggle" | "select" | "custom";
  options?: unknown;
};
```

**收益**：设置搜索、设置项级持久化、门禁断言"每个 entry 都有可见控件"三件事一次性获得。

## 6 可拖宽列（v2，2026-11-09）

**这一节是"同类只改一处"那条反例的落码结论**：拖宽能力的**唯一实现**是
`frontend/src/design/resize-column.tsx` 的 `<ResizeColumn>`，**不存在**第二套。

### 6.1 契约（写清楚以后不会被漏掉）

| 规则 | 说明 |
|---|---|
| **任何可拖宽区域必须用 `<ResizeColumn resizeKey="cX" ...>`** | 它同时提供：逐帧跟手的拖动（写 DOM + rAF 合并）、把手指向、命中区、hover 高亮 |
| **拖动目标靠 `data-resize-key` 属性找，不靠映射表** | 旧实现有一张 `{c1:"agents", c2:"sessions"}` 手写表，于是 c5/c4/c4t 三处被漏掉（两个"松手才跳"、一个"连按都按不到"） |
| **组件自带 `overflow-visible`** | 把手溢出到列外 4px；父级 `overflow-hidden` 会裁掉一半 → `elementFromPoint` 落到相邻区域 → 鼠标按不到。要裁切请放 children 内层 |
| `as` 决定标签 | 与主内容并列的侧栏用 `aside`（默认），面板内部的子列（文件树）用 `div` |
| **把手 z-index ≥ 30** | 必须高于列内任何内容（页签行、文件列表），否则被盖住就拖不动 |

五个实际使用点：`c1` 助手列、`c2` 会话列、`c4` 文件面板、`c4t` 文件树、`c5` 完整历史。

### 6.2 拖动语义与上限（同一套，不许各写一支）

**语义（2026-11-10 用户裁决「拖哪条边哪条边跟手」）**：把手在屏幕上的坐标必须逐帧贴着鼠标；
内层（树）变宽吃的是**同级**（查看器）的宽，不是外层面板的总宽，更不是左列。把手到边就停，
不反向补偿（宽度数值对了方向感全错是这类实现的毒性，见 6.4 反例）。

| 列 | 真实上限 | 依据 |
|---|---|---|
| `c1` / `c2` | `视口 − RAIL − 另一列 − MIN_CHAT − HANDLE_HIT` | 不压破聊天保底 |
| `c4` / `c5` | `视口 − RAIL − c1 − c2 − MIN_CHAT − HANDLE_HIT` | 同上 |
| `c4t` | `面板 − MIN_VIEWER` | 文件树不能超出它所在的面板（`layout()` 里 `tree = min(c4t, panel − MIN_VIEWER)`）；写成视口会在松手时回弹 |

**MIN_VIEWER = 160（2026-11-10，原 206）**：受压实测（页签行/工具栏/正文全是 overflow-x-auto，
压到 160 出的是滚动条不是溢出） + 与树下限 160 对称 + 树可拖行程显著变长。

**常量表只做技术兜底**（`SANITY = 4096`）：`WIDTH_LIMITS` 里除了带产品依据的上下限，
不许再出现"看起来合理"的数字（协议 §3.13）。`c1` 曾经的 `440` 与 `c2` 被否掉的 440 同源，
造成"拖助手列 8/50 步不动、拖会话列 0/50 步不动"—— 两列手感不同。

### 6.3 机器检查（`frontend/test/ui-contract.mjs`）

**不枚举具体列**，而是**枚举页面上所有 `[data-resize-key]`**，在三个场景（默认 / 完整历史 /
文件面板+树）各自验证：

1. 每个区域都有一个**可命中**的把手（`elementFromPoint` 命中把手本身）；
2. 拖动时宽度**逐帧变化**（不是松手才跳）；
3. 拖动过程中**无长任务**（>50ms 阻塞）；
4. 两列拖到墙后聊天列宽度一致（同一套上限规则）；
5. **分隔条跟手**（嵌套拖动块：把手 x 位移 = 鼠标位移，面板/左列宽度不变 —— 2026-11-10 新增）。

新增可拖区域只要写 `<ResizeColumn>` 就自动被这五条覆盖；漏写属性或把手被裁都会红。

### 6.4 反例：「宽度对了，方向感全错」与「松手后列被内容顶宽」

- **2026-11-10 用户**：「我往右拖呢，它在往左边扩张。」
  实测（1600，拖树 +100）：把手 x **恒为 1237 不动**，面板左缘反而 1000→900——
  旧版把「树变宽」实现成「整块面板变宽」，两条边的位移正好抵消。
  配套的「从左列借宽」还被借走不还（c2 300→240）。修复：`dragCascade` 重写为「树吃查看器」；
  借宽路径整个删除（想让面板更宽拖外层 `c4` 把手，两套语义不串场）。
- 同日第二案：松手时把 inline 宽度清掉交还给 React——但拖到钳制值（状态无变化）时
  React 不重渲染，列宽跌回 **min-content**（实测 444→527，文件内容把面板顶宽）。
  修复：inline 保留（它就是要渲染的值），状态变化时由 React 覆写。
- **教训**：拖动的验收必须断言**几何**（把手的 x 坐标），不能只断言**宽度**——
  宽度数值全对、方向感全错的实现，宽度断言恒绿。
