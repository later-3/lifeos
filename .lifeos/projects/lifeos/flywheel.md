# 飞轮

> 角色：经验　类型：文档　状态：现行

飞轮是可复用的经验：反复奏效的做法、反复踩的坑、以及为什么（协议 §3.1）。

- 每条尽量写成"一句可复用的结论 + 依据（案例编号或任务路径）"；
- 过程写在日志里，事实写在案例里，这里只放提炼出的经验；
- 没有可复用结论时不强行写。
## 结论

- **运行/回合的"真相"必须由服务端持有，前端只消费派生事实**：一切状态判断、尤其首回合对账、都不得只靠前端缓存推进——第二次出现"像断流/心跳误报/排队丢失"这类问题，先改服务端再改前端。参照 piweb/LibreChat 服务端裁决 + 对账。（依据：2026-10-24 案例 C113、Task 0002 第 1 包）
- **参考要落到端点/事件/UI 位置**：不满足"像 XX 的做法"这种描述；每条必须指向"参考项目哪个端点/事件/位置、何时刷新、失败动作"——不然会返工三次仍不彻底。（依据：2026-10-24 案例 C114、参考基线"参考映射"节）

- **完成/终态判定必须看终态字段，不能看"存在性"**：判断一环（回合一/receiving）是否结束，要看 `stopReason` 的终态（stop/length/error），不能"有 assistant 就算完"；用户打断（aborted）属"中断"，不能报"已完成"。（依据：2026-10-24 案例 C116、Task 0003）
- **开发时不要在真实会话运行时 live-edit 服务端源码**：`node --watch` 会重启子进程，静默杀死在跑的回合（无错误、无收尾）；真实使用用独立端口 + 独立 `LIFEOS_HOME` 或 `pnpm start`。（依据：2026-10-24 C116、`evidence/2026-10-24-03-进程与日志时间点.md`）
- **任务必须用共享实现创建**（`createTask` → `ensureTaskSkeleton`），不要手工 `mkdir` + 手写 `task.md`：手工建会漏骨架、类型校验与目录说明（本次 0003 手工建导致 `home:check` 报 8 处错误）。（依据：2026-10-24 Task 0003 log「过程复盘」）
- **写中文文档不要用未加引号的 heredoc**：`<<EOF` 会把反引号里的内容当命令执行，静默吞掉正文并留下半截句子；一律用 `<<'EOF'` 或文件编辑工具。（依据：2026-10-24 Task 0003 log 复盘第 2 条）
- **重装/替换家目录数据文件前必须先停后端**：旧进程会用内存中的陈旧叶 id 继续追加，把 parent 链写断，导致消息从 branch 上"消失"（列表有、详情 0 条）。正确顺序：停服务 → 备份 → 重装 → 起服务。（依据：2026-10-24 案例 C117）
- **SSE 用 snapshot-first：先订阅缓冲、再发快照、再 flush；所有事件消费者共用同一套守卫（seq 基线 + turnId）**：同一份流出现两个消费点时，必须抽出统一守卫，不能一处去重一处不去重。（依据：2026-10-24 C119、Task 0005）
- **截图基线只比骨架**：usage/时间/真实会话正文这类"用户一用就变"的区域必须 `data-shot-mask`；否则门禁会因正常使用而假红，最后没人再信截图红。（依据：2026-10-24 状态条 usage 漂移使 5 张基线假红 0.09–0.43%）
- **运行实例不带 watch**：用户实例用 `pnpm start`（构建产物）；`pnpm dev`（`--watch`）只给隔离开发实例。否则一次源码保存就会重启进程、杀掉正在跑的回合。（依据：2026-10-24 C119 根因 B）

- **默认跟随是"模型 + 思考级别"一整套**：只在新建时应用不算跟随；恢复会话也要按配置裁决，且必须用显式标记区分"用户选过"与"默认"。缓存键同理必须带完整作用域（agent+project+id）。（依据：C120）
- **开发工具必须强制规范，不能只写一条规范**：规范 §7 写了"运行实例不带 watch"，我仍然在回合中途保存源码、杀掉了回合。修复是让 `pnpm dev` 本身不会杀回合（supervisor：先排空、等在跑的回合、只重启一次），而不是再加一条规范。（依据：2026-10-25 C121）
- **参考基线只认上游默认分支的最新 commit**：必须写 remote/branch/commit/日期四项；`git rev-parse HEAD` 只是当前检出分支，我们自己的 fork 不算参考。曾把 fork `f3a5c91`（2026-08-28）当成 pi-web HEAD，把上游 `e533d9b`（2026-10-20）当成"旧版"，导致"上游退化"的错误结论。（依据：2026-10-25 C129，修正 C122）
- **后台完成类提示 = 服务端事实 + 焦点路由 + 过载即断线**：运行态与未读放服务端、回合级全播、细节级只给焦点、过载关闭让客户端重连重快照。（依据：2026-10-25 C122）
- **状态只存一份事实，聚合只做派生**：会话/项目/Agent 的状态如果各自存一份，三层会逐渐不一致（0007 的孤儿未读、0008 的未读颜色漂移都是这类）。事实在服务端（带完整归属），派生在纯函数里，语义写在一处并被代码引用。（依据：2026-10-25 C125）
- **颜色语义要对照拍板，不对照实现**：实现会悄悄漂移（拍板是绿色，界面成了蓝色，用户看着就以为是别的状态）。改颜色前先查拍板原文。（依据：2026-10-25 C125）
- **同一位置的数字只能有一种含义，层级计数要逐层用数字例子定义**：项目行上曾同时显示"会话总数"和"未读数"，用户分不清；Agent 层的数字被我误定为会话数之和，而正确语义是"待看的 Project 数"。规则写成数字例子（3 个未看、看 1 个 → 变化），再写代码。（依据：2026-10-25 C126）
- **决策必须先查再提**：数字与选项要先查约束（源码、实测、官方文档），再提问；不能先拍一个数字再找理由。协议 §3.12 把这条写成了必须。（依据：2026-10-25 C128）

- **规范写进文件不等于会被执行**：提出决策前必须逐项核对协议 §3.12 的七项，缺项不得提问；没有参考实现或实测支撑的约束一律不设（§3.13）。（依据：2026-10-25 C130）
- **参考实现给的参数直接照抄，不自创**：pi-web 客户端压缩的 1MB 阈值、1024px、q0.85 都是现成参数，没有理由自己另定一套。（依据：2026-10-25 C130）
- **能力类结论要跑够样本**：至少 5 次，写命中率与失败样本；单次异常先复测再下结论。（依据：2026-10-25 C131，模型看图 4/5 正确但颜色抖动）
- **约束数字集中到一处，并用文档一致性测试锁住**：数字写在代码常量里，文档表格由测试逐项比对，改一处不改另一处就红。（依据：2026-10-25 图片输入 `test/image-input-doc.test.mjs`）
- **纯函数测试通过 ≠ 功能可用**：用户可见的功能要有一次真实链路断言（界面计数/刷新后仍在）。（依据：2026-10-25 C132）
- **界面要覆盖"还没有这个东西"的状态**：状态存会话里，就要回答"没会话时显示什么"；能显示默认值时才显示，不能显示时必须明确缺席，绝不用默认值顶替"有会话但该值缺失"（那会撒谎）。（依据：2026-10-25 C133 头部 task 段）
- **写操作要么完成要么不留痕迹**：一次绑定里有多步写入时，后续步骤失败要回滚"本次新建"的部分（且绝不能删搬过来的、含用户数据的目录），并给可读错误码；不能留"列表里有但一用就 500"的半成品。（依据：2026-10-25 C134）
- **全局 onError 是基础设施**：没有它，任何未捕获异常都退化成纯文本 500，界面只能说"请求失败"。（依据：2026-10-25 C134）
- **不要为已有语义另造入口**：切换 Task 已经由"进入"表达（建即进入、按编号接手），再做一个 `/task` 命令就是同一件事的第二个入口——多一个入口就多一套要维护、要测试、要和协议对账的东西。（依据：2026-10-25 C135）
- **流程步骤要能被推导出来**：任何"先选 X 再 Y"的流程，先问"不做这一步会怎样"；如果系统已有默认值能让 Y 正常工作，这一步就是自造的。（依据：2026-10-25 C135，"新建会话前先选 Task"）
