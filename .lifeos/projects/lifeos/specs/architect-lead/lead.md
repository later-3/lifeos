# 架构师统筹规范（多 Agent 开发的规划与流程）

> 角色：架构 / 协作　类型：规范　状态：现行（2026-10-31）
> 适用：本项目（Life OS）由架构师牵头、多 Agent 分工实施的需求开发。
> 阶段的具体内容随任务变化，本文只写**怎么统筹**；实例化的内容写进对应任务的文档（04 阶段任务书等）。

## 怎么用

架构师接手一个需求开发时对照 §2 每一条；开发/测试/检视 Agent 若发现统筹动作缺失，按本文条文指出。

## 2 条文

### 2.1 需求先拍板再立项：岔路口给选项，拍板结果进背景文档

- 必须：与用户澄清需求时，把方案岔路（数据源策略、实时/轮次、范围、二期边界）用"决策点 + ≥2 选项（含维持现状）+ 优劣 + 推荐 + 依据"格式提出（协议 §3.12）；拍板结论**集中写进任务的 `01-background.md`**，后续所有文档只引用不复述。
- 可以：依据不足的事项先查源码/实测/官方文档再问；查不到就明说"无法估计"，不开空头支票。
- 反例：把未推导的数字当建议提出（C159 类反面案例，见协议 §3.12 依据一行）。

### 2.2 架构文档表达"必须守住什么"，不锁死实现

- 必须：架构文档区分两层——**硬的**（契约口径、数据/事件事实源、安全边界、验收标准、阶段收口）与**软的**（内部结构、组件组织、可选技术路线）。软的部分明确声明"这是实施者的思考空间"。
- 必须：为每句验收提供一个可端到端复核的"验收句"（用户视角、一句话可判真伪），端到端测试以这些句子为版本。
- 不应该：在拿不准实现细节的地方写死实现；表述不清的代价是开发者按猜写——写不了的就标"留给实施者提案拍板"。

### 2.3 文档是唯一交接物；歧义的处置是改文档，不是口头解释

- 必须：向开发/测试 Agent 交接，只走文档（契约、任务书）；AGENT 的反串讲回执出现歧义时，修订原文档并记录一行变更说明，不靠聊天补丁。
- 必须：所有跨 Agent 的裁决写进架构师任务的 `log.md`（全局台账），各家自己的过程写各自 log（协议 §3.8 日志不搬家）。

### 2.4 拆阶段按"可独立验证"切分，不做时间估算驱动

- 必须：阶段划分以**每个阶段都有可验证的收口产物**为准（先契约后分头；哪些任务做完要前后端联调，由架构师在阶段表里点名联调节点与触发条件）；阶段数量随任务规模伸缩，一个阶段收敛成 2–4 个小任务（每个任务要有：目标、背景/方案、测试方法、谁负责）。
- 应该：先把"纯后端可通 + 前端 mock 可并行"的阶段排在联调之前，让两端不需要共同等待。
- 反例：一个阶段横跨"接口、事件、三个前端页面"却定义不出能验证的中间收口。

### 2.5 五环闭环：交接 → 反串讲 → 开发自测 → 检视 → 端到端，架构师全程参与

| 环节 | 输出 | 完成定义 |
|---|---|---|
| 1 交接 | 架构文档 + 阶段任务书（按人分节，含范围/不做/验收/纪律引用） | 任务书无歧义待反串讲 |
| 2 反串讲 | 每个 Agent 的回执（复述理解 + 疑问） + 架构师逐条回应 | 回应后文档无未决歧义 → 标"冻结"，开放分歧点列明（当场拍板或升级用户） |
| 3 开发+自测 | 代码 + 自测证据（测试输出/截图）+ 交付回执（改了什么/验证了什么/开放问题/影响面） | 开发声明满足任务书验收 |
| 4 检视 | 检视报告（四类结论分级：缺陷/质量缺口/架构缺口/功能缺失；功能缺失只登记 todo） | P0/P1 清零；检视过 → 允许进入端到端 |
| 5 端到端（里程碑） | E2E 报告 + evidence（录屏/截图 + 请求摘录） | 验收句全绿 → 阶段收口 |
| 6 审阅+交付 | 架构师审阅记录（效果满足验收 + 未打乱既有架构边界）+ 给用户的交付摘要（变更/证据/预览地址） | 用户确认 = 阶段关闭 |

- 必须：问题升级给用户时按协议 §3.12 决策格式；过程中发现的规范缺陷回到本文修订，不把个案当惯例。

### 2.6 分工的测算线：谁测自己的东西，谁测联合的东西

- 必须：前端/后端各测各自单元（含失败路径）；专职测试 Agent 只做端到端真链路；检视 Agent 按四类检视进入。
- 必须：架构师收口时审"效果与架构"，两问都要有证据：验收句是否全绿；新建模块有没有越出既有边界（呈现层只消费派生层、写层广播、模板=唯一事实源等既有约束仍在）。

### 2.7 历史不改写，过程可追溯

- 必须：阶段的契约与任务书修订用"冻结版标注 + 变更说明"推进，不重写历史；E2E 与检视证据进任务 `evidence/`。
