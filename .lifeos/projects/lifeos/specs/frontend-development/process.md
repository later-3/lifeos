# 前端开发流程（固定四步）

> 角色：开发规范　类型：流程　状态：现状（2026-10-21）
>
> 前端 = 用户能看到的页面、布局、交互、响应式和视觉。任何前端改动都按本文走。
> 本文只写**怎么执行**；具体做成什么样，在 [`.lifeos/projects/lifeos/specs/frontend-development/frontend-spec.md`](./frontend-spec.md)、页面文档和 [`reference-baseline.md`](../../knowledge/reference-baseline.md)。

## 0. 先记住两件事

1. **遵守什么规范**：统一规范 + 当前页面文档 + 参考基线。
2. **怎么执行规范**：本文的四步。缺一步都不算完成。

**Agent 入口**：仓库根 `AGENTS.md` → 本目录的 `specs/frontend-development/`（`process.md` → `frontend-spec.md`）→ 当前页面设计。任何 Agent 接手 Life OS 前端任务，先读本文，再读规范/页面文档；不要凭“看起来差不多”直接写代码。

## 1. 四步门禁

| 步骤 | 必须做什么 | 产出 | 不通过就停 |
|---|---|---|---|
| **1. 核对现有规范** | 判断前端类型；逐项对照规范；列缺口 | 规范覆盖表 | 缺口未登记，不写代码 |
| **2. 补齐缺失规范** | 按场景选参考；提取证据；写规范 diff 和验收断言 | 参考行 + 规范/页面 diff + 断言 | 没有证据或用户没拍板，不写代码 |
| **3. 按规范开发** | 先线框/状态矩阵，再实现；只用已写下的规范 | 页面文档 + 代码 + 测试 + 截图 | 出现规范外的新模式，退回 Step 2 |
| **4. 回头复盘** | 检查规范是否合理；修订或删除错误规则 | 规范修订 / 案例 / 飞轮 | 不复盘不算完成 |

**“固定”不等于每个任务都写长文**：小改动第 1 步可以只有一行“现有规范已覆盖”，第 2 步写 N/A 并说明理由；顺序不能跳。

### 1.0 先列任务全貌，再报进度

四步是**固定元流程**；具体任务还要拆成可验收的步骤。开工前先写清：

```text
任务：手机返回/适配
总步骤：7
当前：2/7
每步：产出 / 门禁 / 需要用户拍板什么 / 失败退回哪一步
```

- 不能只说“Step 1”“走完第一步”——必须说“**任务步骤 x/N**”；
- 每次汇报都带 `x/N` 和剩余步骤；N 变了要说明为什么；
- 四步元流程与任务步骤分开命名，避免把“补规范”误当成任务结束；
- 任务没有走到验证和复盘，不算完成。

### 1.1 Step 1：核对现有规范

先判定这次改动属于哪些类型：

| 维度 | 例子 |
|---|---|
| 页面 | 根视图、列表-详情、设置、资料编辑、空态 |
| 表面 | 页面、全屏面板、浮层、Sheet、确认框 |
| 设备 | 桌面、手机、平板、横屏 |
| 交互 | 导航/返回、表单、流式、滚动、键盘、手势 |
| 数据呈现 | 消息、工具、用量、文件、关系 |
| 视觉 | token、密度、字号、间距、动效 |

然后写规范覆盖表，放在任务或页面文档里。下面只是格式示例，不是当前任务的已知缺口：

```text
需求点        适用规范                         现状        缺口/动作
手机返回       frontend-spec §3.2 / 页面移动端   不完整      补返回栈与系统返回
状态条         chat.md §4 / frontend-spec §5     已覆盖      无需补
```

判定只有四种：

- **covered**：已有规则且可验收；
- **outdated**：规则与当前事实不一致，必须先改；
- **missing**：没有对应规则；
- **untestable**：写了但无法用测试/走查证明，按缺口处理。

**硬规则**：

- 桌面规范不能直接套手机；手机是独立布局和交互模式；
- 页面文档没有写到的状态/交互，不算“实现时再说”，算缺口；
- 找不到对应规范时，不许用“行业惯例”补，进入 Step 2。

### 1.2 Step 2：补齐缺失规范

#### 参考怎么选

- **按场景选 2–3 个**，不把所有产品都看一遍；
- **开源优先**：能读到源码、能本地运行、能核对 commit 的优先；
- **闭源只做补充**：官方文档、实机截图/录屏，标“观察”，不假装抠了源码；
- 闭源抠取成本过高时，**换一个优秀的开源同类**，不强上；
- 参考的是**页面交互、信息层级、视觉语言**，不是业务功能、品牌色或产品玩法；
- 每个场景的参考行只写进 [`reference-baseline.md`](../../knowledge/reference-baseline.md)，不另建参考清单。

#### 参考原则：先解释，再借

只写“某项目是怎么做的”是表面功夫。每个候选参考必须回答五个问题，缺一不可：

1. **为什么这样设计**：它要解决什么用户问题/技术约束？
2. **好处是什么**：在什么情况下让体验或工程变好？
3. **适用条件与代价**：什么时候不适用，付出了什么复杂度/空间/学习成本？
4. **我们是什么情况**：Life OS 的数据、用户、场景、运行时约束与它有什么同/不同？
5. **我们的倾向**：全盘采用 / 只借结构 / 只借行为 / 只借视觉 / 不适用，并写明理由。

因此，Step 2 的参考矩阵必须长这样：

| 参考 | 为什么这样设计 | 好处 | 适用条件与代价 | Life OS 现状 | 倾向 |
|---|---|---|---|---|---|
| ... | ... | ... | ... | ... | 采用 / 部分采用 / 不采用 |

“借什么/不借什么”是这份分析的结论，不能代替分析本身。

#### 倾向是场景函数，不是永久判决

- 参考项目的“采用/不采用”**顺着当前页面的功能、数据类型、用户任务和设备场景走**，不是把某产品规定成永远的样板。
- 页面功能或数据模型变化（例如新增附件、排队语义改变、从桌面扩展到手机、从单实体变多实体）时，**必须回到 Step 1 重新做覆盖评估，再回 Step 2 重看参考**，不能沿用旧倾向。
- “这次不采用”只是当前场景的结论；原因是数据/内容不匹配时，要把**匹配条件**一起记下来，下次场景变了可以重新匹配。
- 每个任务的详细拆解写在任务自己的 `02-references.md`（或等价任务文档）；任务完成后，把可复用的“为什么/好处/适用/倾向/复核触发”回填到 `reference-baseline.md` 对应场景行，**不另建第三份参考清单**。

拆解卡最小格式：

```text
场景 / 需求：
参考：项目 + 文件/版本
为什么这样设计：
好处：
适用条件与代价：
Life OS 当前情况：
当前倾向：
复核触发：需求/数据/设备/参考版本变了就要重评
```

#### 证据分级

| 级别 | 证据 | 能否作为规范 |
|---|---|---|
| A | 开源源码：repo + 文件路径 + commit | 可以 |
| B | 官方文档：URL + 日期 | 可以，注明是文档行为 |
| C | 实机观察：设备/系统/App 版本 + 截图或录屏 | 可以，注明是观察 |
| D | 推断、“行业惯例”、“大概这样” | **不可以**，只能作为待验证假设 |

参考产品会变。写规范时记录**日期/commit/版本**；下次使用先重新核对，不把旧观察当永久事实。

#### 补齐什么

每个缺口至少产出三样：

1. **参考矩阵 + 参考行**：先写“为什么/好处/适用条件/我们的情况/倾向”，再落到 `reference-baseline.md` 的“借什么 / 不借什么”；
2. **规范 diff**：改 `frontend-spec`、页面文档或新增主题规范；只写能执行、能验收的规则；
3. **验收断言**：测试或人工走查怎么证明这条规则成立。

导航、布局、视觉这类选择题，不只给一句结论：

- 先给 **2 个具体模型**（线框/截图/行为说明）；
- 每个模型写清返回、系统返回、焦点、滚动、状态保持的差异；
- 用户基于对照拍板，不要求用户凭空想象。

**用户没拍板前不写代码。**

### 1.3 Step 3：按规范开发

- 先补齐页面文档：背景/意图、数据、关系、用户任务、交互、布局/参考、状态、移动端差异、验收；
- 先画线框/区域顺序，再写组件；
- 只用 `design/tokens.css`、`design/ui.tsx`、`design/layout.ts` 和已登记的 primitive；
- 实现中发现规范没覆盖的情况：**停下来，退回 Step 2**，不静默加新模式；
- 完成后跑 `pnpm verify` / `pnpm build`，视觉变化必须看截图 diff。

#### 对象完整性

用户感知为**一个对象**的东西，必须作为一个整体呈现：

- 一条消息、一轮对话、一个文件、一张表单；
- 同一对象的信息、状态、动作放在同一区域/同一组件；
- 内部可以分组、左右布局，但不能把同一对象的动作拆到不相邻的区域，变成“这里一个按钮、那里一个按钮”。

例：`TurnStatusBar` 是“这一轮”的一个整体；步骤、耗时、重试、tokens、速度可以分左右/分组，但用户应该一眼看出它们属于同一轮。

#### Pi TUI 基线

会话类前端必须对照当前 Pi TUI 的交互基线；发现差距就登记 `.lifeos/projects/lifeos/todo/todo.md` 并排期，不得以“前端更丰富”为理由缺失。

Pi TUI 的 `↓ Jump to latest message` / 回到底部已作为手机与桌面共同基线写入 [`mobile.md`](../frontend-mobile/mobile.md) 与 `chat.md`；新增差距继续登记 `.lifeos/projects/lifeos/todo/todo.md`。

### 1.4 Step 4：回头复盘

实现完成、合并/交付前回答：

1. 哪条规范预测对了？
2. 哪条规范在实现中被证明是错的/不够？
3. 哪条参考被误读了（只借了皮肤，没借上下文）？
4. 哪个测试/走查没覆盖？
5. 同类任务下次能不能直接复用这套规范？

只要有一条答案是“没有/不知道”，就补规范或补断言。规范错了就改，不把错误规则供起来。

## 2. 产物放在哪

| 产物 | 落点 |
|---|---|
| 规范覆盖表 | 任务 `task.md` 或当前页面文档；不新建登记表 |
| 参考行 | `.lifeos/projects/lifeos/knowledge/reference-baseline.md` |
| 跨页面规则 | `.lifeos/projects/lifeos/specs/frontend-development/frontend-spec.md` 或按主题拆出的 `.lifeos/projects/lifeos/knowledge/design/<topic>.md` |
| 页面差异 | `.lifeos/projects/lifeos/knowledge/design/<page>.md` |
| 验收断言 | `frontend/test/*` 或页面文档的“设计验收” |
| 复盘 | 案例/飞轮；规范错误同轮修订 |

## 3. 参考代码库

源码参考统一放在仓库外的本机目录（建议 `~/Code/reference/`，不进 Life OS Git）：

- 每个条目记录 repo、branch、当前 commit、用途、最后核对日期；
- 只作为阅读/对照，不把参考代码复制进 Life OS；
- 更新前先看 `git status`，不覆盖本地改动；不自动 pull 脏工作区；
- 开源参考优先；闭源产品只保留截图/录屏/官方文档。

具体参考项目按场景写入 `reference-baseline.md`，不在这里复制第二份清单。

## 4. Agent 模拟验收

流程和入口改完后，必须用**不知道流程的新 Agent**做一次模拟：

1. 只给仓库路径和一个前端需求；
2. 不告诉它“先读哪个文件”、不告诉它四步；
3. 让它先说明会读什么、按什么步骤做、什么时候停止；
4. 检查它是否从仓库根 `AGENTS.md` 找到本流程，是否能复述四步，是否发现缺少的手机规范并停在 Step 2。

失败就改入口/文档，不改 Agent 的“自觉”。大改流程或文档结构后重复一次。

## 5. 反模式

- 先写代码，再补规范；
- 只写“参考了 X”，没有路径、版本、行为、借/不借；
- 把参考产品的皮肤/品牌色搬进来，忽略信息层级和上下文；
- 用桌面规范直接做手机；
- 同一个用户对象的动作散落在多个区域；
- 规范写了但无法验收；
- 复盘只写“完成了”，不检查规范是否合理。

## 6. 完成定义

- [ ] 规范覆盖表已写，缺口已处理或明确 N/A；
- [ ] 参考证据达到 A/B/C，D 没有被当成规则；
- [ ] 规范/页面文档已更新，且有验收断言；
- [ ] 用户已对参考/模型/规范拍板；
- [ ] 代码只使用已登记规范与 primitive；
- [ ] `pnpm verify` / `pnpm build` 通过；
- [ ] 桌面/手机/横屏按范围验收；
- [ ] 复盘完成，规范错误已修订。
