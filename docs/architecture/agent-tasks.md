> 角色：架构　类型：说明　状态：**详细设计（Agent 定义线的"任务"板块）**；标 【待批】的地方需要顶层确认

## 1 对象：任务由三样东西构成

| 名字 | 是什么 | 生命周期 |
|---|---|---|
| **任务（登记项）** | "要做什么 + 什么时候做 + 产出放哪"的登记；**含任务类型**（见下） | 长期存在，可暂停/恢复/取消 |
| **运行** | 每次触发产生的一次执行 | 一次性；**每次 = 一次会话 + 一条记录 + 一份产出** |
| **产出** | 这次运行留下的东西（文件/动态/通知） | 按任务约定落位 |

**两层分工（用户给的框架）**：

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| ① **公共层** | 登记（在什么时刻要做一条任务）+ 到点**触发对应的 Agent** | 不关心任务内容是什么 |
| ② **任务内容**（属于 Agent） | 登记的"提示词"就是内容；触发时由 **Agent 根据当时上下文自己把提示词整理好**再执行 | 不负责计时 |

**任务类型（现有实现里的字段，必须带上）**：登记项包含
- `taskType`：**任务领域**（例如 `development`；与项目声明的任务类型**同一命名空间**，缺省取项目声明）；
- `taskCategory`：**任务类别**（交付物性质：`design` / `feature` / `refactor` / `protocol` / `research` / `review` / `fix`）。
（来源：pi-004 D8/D9 已落地字段，见 `src/long-agents/tasks/contract.ts`。）

## 1.1 它在交互 harness「任务」分类中的位置（2026-10-15 定）

协议把**任务（总类）**分成两类（见 [`.lifeos/interaction-harness/protocol.md`](../../.lifeos/interaction-harness/protocol.md) §3.8）：

| 类型 | 谁发起 | 我们这份文档对应的是 |
|---|---|---|
| **用户下达任务**（交互 harness 协议任务） | 用户在对话里下达（"做个需求""定位这个问题"） | 它的工作单元形态（一任务一目录 + `task.md`）**已存在** |
| **Agent 定时任务** | **系统**按时间/事件触发，无人值守、反复运行 | ✅ **本文档就是这一类** |

**关系**：两类**同宗同源**——共用 `taskType`（领域）与 `taskCategory`（类别）同一命名空间、同一目录约定；区别只在**触发方式与生命周期**（用户发起且一次收束 vs 系统发起且反复运行）。
定时任务的**一次运行**（run）是它独有的概念：每次触发 = 一次执行 + 一个独立会话 + 一条运行记录 + 一份产出。

## 2 任务怎么产生（不做"填表建任务"）

| 路径 | 过程 |
|---|---|
| (a) 用户直接提出 | 用户在对话里说需求（"每天写日记，我要知道你干了什么"）→ **Agent 识别**是否需要定时任务 → 与用户确认 → 用工具登记 |
| (b) Agent 主动识别 | 交互中 Agent 发现潜在需求 → 问用户"要不要我建个定时任务？" → 用户确认 → 登记 |

- **任务描述（提示词）由 Agent 自己写**（依据用户原话 + 当时上下文组织），用户**只描述需求**；
- **前端不做表单**；前端只做**查看与管理**：任务列表（名称、触发方式、**下次运行**、状态、**最近一次结果**）＋ 暂停/恢复/立即跑。

## 3 一次触发的完整流程

```
公共层：到点  →  找到这条任务登记的 Agent
   ↓
起一次会话（这次运行的会话）
   ↓
注入任务上下文：登记的提示词 + 上次运行结果/失败原因 + 产出约定 + 当时的项目与日期
   ↓
Agent 组织成完整提示词（"根据当时上下文自己整理"）→ 执行（用它的工具）
   ↓
产出按约定落位（任务目录 outputs/ 或 daily/、social/ 等）
   ↓
写运行记录（时间、结果、失败原因、产出指针）
   ↓
（可选）告知用户：通知 / 朋友圈动态（social_manage）
```

## 4 落点（详细设计的核心）【待批】

```
~/.lifeos/agents/<agentId>/projects/<projectId>/tasks/<slug>-<id8>/
├─ task.md        任务说明书（现状已有：建任务时按模板生成）
├─ task.json      登记信息：提示词、触发（once/cron/event）、时区、产出约定、状态、下次运行 ← 目标位置
├─ sessions/      每次运行的会话文件（一次运行一个）
├─ runs/          每次运行的记录（时间、状态、失败原因、产出指针）
└─ outputs/       该任务的产出（或按约定写入 daily/、social/ 等既有位置）
```

## 5 Agent 怎么知道这件事（两条通道）

**① prompt 区域里的一段说明**（用户定："只需要给一段提示词，别复杂化"）——要讲清：
- 系统有"定时任务"这套机制；你**可以登记/查询/暂停/立即跑**自己的任务；
- 任务描述（提示词）怎么写；**产出放在哪**（产出约定）；
- 触发时你会拿到什么（登记信息 + 上次结果 + 当时上下文）。

**② 工具面**：`task_manage`（现状 8 个动作：`list / create / update / pause / resume / cancel / run / cancel-run`，创建会自动落地任务目录与 `task.md`，修改用 `expectedRevision`，任务上下文**冻结在创建时的项目**）。
【待补】两个动作：**查某任务的运行历史**、**在任务轮里知道自己"第几次运行 + 上次结果"**（数据已在 occurrence 里，缺的是暴露方式）。

## 6 你的四个问题，逐一回答

| 问题 | 答案 |
|---|---|
| ① 系统怎么触发 | 公共层按时钟到点 → 触发登记里指定的 Agent → **起一次会话** |
| ② 触发后产生了东西/要告知用户 | 产出按约定落位（`outputs/`、`daily/`、`social/`）；告知走**通知/朋友圈**（"投递到外部渠道"暂不做） |
| ③ 它怎么知道要提供什么 | prompt 区域的"任务机制说明" + 工具面（登记/查询）+ 任务轮注入的上下文 |
| ④ 它怎么知道做了哪些任务 | `task_manage list`（任务与状态）+ 任务目录里的 `sessions/`（做过什么）+ `runs/`（结果/失败） |

## 7 闭环（对应用户给的两条）

| 闭环要求 | 怎么成立 |
|---|---|
| (a) 管理与触发**绑定** | 登记里带 `longAgentId`（触发时按它找人）；Agent 用 `task_manage` 管自己的任务；触发上下文与登记信息同源 |
| (b) 会话**可追溯** | 每次运行的会话在任务目录 `sessions/` 里；occurrence 记录 `originSessionId` → Agent 能读到自己做过什么 |

## 8 不变量与验收（实现时的判据）

1. 同一任务同一时刻**只跑一次**；每次运行**必有**会话 + 记录；
2. 触发上下文与登记信息**同源**（不能在触发时另造一套描述）；
3. **产出可定位**（任务目录或约定位置能找到）；
4. Agent 能**查到自己有哪些任务、每条任务跑成没成**；
5. 任务目录**人也能看懂**（说明书 + 登记 + 会话 + 记录 + 产出）。
