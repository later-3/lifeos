# 代码检视与缺陷分级

> 角色：开发规范　类型：决策　状态：现状

## 1 为什么有这份文档

用户 2026-10-19 的原话：**"缺陷是缺陷，功能是功能"**。检视是为了把**已有的东西做对**，
不是为了把别的项目有的功能都补上。"顶级项目"不等于"功能多"，而是**逻辑、质量、架构、
呈现**四项都说得清、都有证据。

反例（已发生）：用户只要求"能看到当前模型用的是什么"，却一度被扩成"恢复默认模型"的完整
功能——那是**新增功能**，不是缺陷修复。登记在 `~/.lifeos/.../cases`（C048）。

## 2 四类检视（按顺序，每类都要落到证据）

| 类 | 看什么 | 证据形式 |
|---|---|---|
| 1 逻辑验证 | 接口的输入/输出/失败路径；空值、重复、并发、进程重启；状态能否闭环到界面 | 单测 / curl 实测 / 浏览器实测 |
| 2 代码质量 | 命名、分层、重复、静默失败、类型、巨型文件、内联 import | `file:line` + 机器门禁结果 |
| 3 Pi 参照 | 是否只用公开 API；语义是否与 Pi 一致（`setModel` 持久化、`tools` 白名单、`noContextFiles` 等） | 引用 Pi 源码具体文件行 |
| 4 标杆对标 | 目录分层、消息零件化、错误/重试呈现、模型选择器等是否有更成熟的范式 | 引用具体项目 + 具体目录/文件 |

## 3 三类结论，分别处理（不许混）

| 结论 | 判定 | 处理 |
|---|---|---|
| **缺陷（bug）** | 实现与文档/声明的行为不一致，或会丢数据/误导用户 | 立即修 + 补失败路径测试 |
| **质量缺口** | 能工作但写法差（重复解析、静默 catch、内联 import、巨型文件） | 拆分或加约束；新代码不得新增 |
| **架构缺口** | 职责错位（读接口建活会话、循环依赖、配置来源双写） | 调整边界，先有测试护栏 |
| 功能缺失 | 现在没有、也没承诺过的能力 | **登记 `docs/todo.md`**，等要的时候再做 |

## 4 交互交付四问（防"表面功夫"）

用户最容易踩的坑：**"我做了个按钮在那儿"**。交付前逐条回答：

1. **用户第一眼看到什么？**——有没有文案/状态/数量，还是只有一个图标？
2. **什么时候看到？**——空态、加载中、失败、重试、长内容、窄窗口，各是什么样？
3. **看到后能做什么？**——有没有明确的下一步动作（重发、切模型、打断）？
4. **键盘和读屏能用吗？**——Enter/Esc/Tab、可访问名、焦点不逃逸。

交付必须附**可复核的证据**：截图（或 UI 断言）+ 实测输出（HTTP 状态、请求体、真实返回）。
没有证据的"我加了"不算完成。

## 5 证据规则

- 先**代码事实**（`file:line`），再**行为实测**，最后才是判断；不靠印象。
- **新接口必须写失败路径**（404/409/400）。只测成功路径 = 没验证（C050）。
- 验证必须在**干净环境**：先清 route mock / 缓存 / 旧 bundle（C047、C039）。
- 用户说"我看到的不对"时，先复现并给证据，不急着改代码。

## 6 已机器化的门禁（能自动查的，不靠自觉）

| 命令 | 管什么 |
|---|---|
| `pnpm typecheck` | 类型（`any` 0 处） |
| `pnpm lint:tokens` | 视觉只用 token |
| `pnpm test` | 接口/文件/装配/流映射（含失败路径） |
| `pnpm test:ui` | 布局几何、对话框、**可见按钮都有可访问名**、截图基线 |
| `pnpm build` | 产物可构建 |
